## 一、Workflow 为什么这么设计

<Callout type="结论">Dify 在“全写代码”和“全交给 Agent”之间选了第三条路：把 AI 应用变成一张**看得见的有向图**，每个节点的输入、输出和出错走向都写在图上，让工程师、产品和业务专家能在同一张图上协作，也让每次运行都能被回放和审计。</Callout>

### 问题背景

一个看似简单的“智能客服”，真正上线时至少包含五六步：理解问题、去知识库找资料、判断这是咨询还是售后、按类型调用不同的模型或工具、把结果整理成固定格式、出错时给一个体面的兜底回复。把这些步骤落地有两种极端做法：

- **全部写成代码**（用 LangChain 之类的框架串起来）：最灵活，但改一句提示词也要工程师发版，产品和业务人员无法参与调优，链路藏在代码里，出错时只能翻日志。
- **全部交给一个 Agent**（给模型一堆工具，让它自己决定怎么做）：搭建最快，但每次走的路径可能不同，成本和耗时不可预测，合规团队无法回答“它为什么这样回复”。

Dify 在 README 里给自己的定位就是“在可视化画布上构建和测试工作流”，并强调“快速从原型走向生产”。画布不是目的，**让步骤显式化**才是目的。

<Source href={D + 'README.md#L92-L116'} label="README.md 的 Key features" />：Workflow、模型支持、Prompt IDE、RAG Pipeline、Agent、LLMOps、后端即服务七项能力，第一项就是 “Build and test powerful AI workflows on a visual canvas”。

### 产品洞察

### 洞察一：画布只是“图”的一个编辑器，图本身才是产品资产

容易误解的一点是：Dify 的可视化并不意味着“低代码玩具”。在当前版本里，执行工作流的引擎已经被拆成一个独立的 Python 包 `graphon`（图执行引擎），Dify 只是它的“宿主”。graphon 的架构文档开宗明义写着它是“可嵌入的 Python 工作流引擎”，支持从 YAML 导入图、构建图、执行图。也就是说，同一张图既可以在画布上拖拽，也可以作为 DSL（领域特定语言，这里指描述工作流的 YAML 文件）导出、评审、放进版本库。

这对产品的意义是：**工作流成了可以复制、分享、迁移的资产**。模板市场、跨环境迁移、把一个工作流当作另一个工作流的“工具”调用，都建立在“图是数据”这个前提上。

<Source href={G + 'ARCHITECTURE.md#L10-L22'} label="graphon ARCHITECTURE.md" />：“Graphon is an embeddable Python workflow engine”，入口包括 YAML 导入 `graphon.dsl.loads`；Dify 在 <Source href={D + 'api/pyproject.toml#L49'} label="api/pyproject.toml" /> 中以 `graphon==0.8.0` 依赖它。

### 洞察二：Chatflow 和 Workflow 是两种“交付形态”，不是两套引擎

Dify 的应用类型枚举里，`advanced-chat` 就是界面上的 <strong>Chatflow（对话流）</strong>，`workflow` 就是 <strong>Workflow（工作流）</strong>。两者共用同一套节点和引擎，区别在于“谁在用、怎么用”：

|  | Chatflow（对话流） | Workflow（工作流） |
| --- | --- | --- |
| 服务谁 | 终端用户在聊天窗口里多轮对话：客服、助手、导购 | 系统或运营人员一次性提交输入：批量处理、报告生成、定时任务、被别的系统调用 |
| 独有能力 | 会话记忆、会话变量（跨轮次保存的状态）、**直接回复（Answer）节点**可以在流程中途多次流式输出 | **结束（End）节点**一次性返回结构化结果；可被定时、Webhook 等触发器启动；可发布成“工具”给其他应用用 |
| 心智模型 | “一场对话里的每一轮都跑一遍图” | “一个函数：输入 → 输出” |

这种区分的代价是概念门槛。第 5 章会看到，高讨论量的 [#9741 “Answer 节点去哪了？”](https://github.com/langgenius/dify/issues/9741)（52 条评论）就是用户在 Workflow 里找 Chatflow 才有的节点。维护者的回答很简短：“这是 workflow，没有 answer 节点，请读文档。”说明这条边界对新用户并不直观。

值得一提的是，枚举里还有第三种图：`rag-pipeline`（知识流水线）。它把“文档怎么入库”也做成了工作流——这是第 3 章的主题。

<Source href={D + 'api/models/model.py#L389-L400'} label="api/models/model.py AppMode" />：`COMPLETION / WORKFLOW / CHAT / ADVANCED_CHAT / AGENT_CHAT / AGENT / CHANNEL / RAG_PIPELINE`；<Source href={G + 'src/graphon/enums.py#L109-L113'} label="graphon enums.py WorkflowType" />：`workflow / chat / rag-pipeline`；会话变量存于 <Source href={D + 'api/models/workflow.py#L240-L241'} label="models/workflow.py" />。

### 洞察三：每个概念都是在回答一个用户问题

把节点、变量、分支、循环、并行、失败分支翻译成用户语言，会发现它们各自解决一个非常具体的困惑：

| 概念 | 对用户意味着什么 | Dify 的具体做法 |
| --- | --- | --- |
| 节点 | “这一步做什么”——每一步都能单独测试、单独看耗时和 token | 内置 20 多种节点：LLM、知识检索、问题分类器、参数提取器、代码、HTTP 请求、工具、模板转换、人工介入…… |
| 变量 | “上一步的结果怎么传给下一步”——用点选代替写胶水代码 | 每个节点的输出进入共享的**变量池**，下游用 `{{#节点.变量#}}` 引用；另有系统变量（如 `sys.query`）、环境变量、会话变量 |
| 分支 | “不同情况走不同的路” | 条件分支与问题分类器选中一条出边；其它出边被标记为“跳过”，跳过会沿着下游一路传递 |
| 循环 / 迭代 | “重复做，直到满足条件” / “对列表里每一项都做一遍” | 循环节点必须设最大次数和退出条件；迭代节点可开并行，并选择出错时“终止 / 继续 / 剔除异常项” |
| 并行 | “几件互不依赖的事同时做，省时间” | 一个节点连出多条边即并行；汇合节点要等所有入边都“有结论”才执行 |
| 失败分支 | “出错了也要有体面的下一步”——把异常当成可设计的路径 | LLM、工具、HTTP、代码、Agent 节点可设重试、默认值或失败分支 |

节点类型见 <Source href={G + 'src/graphon/enums.py#L15-L45'} label="graphon enums.py BuiltinNodeTypes" />；循环上限与退出条件见 <Source href={G + 'src/graphon/nodes/loop/entities.py#L37-L46'} label="loop/entities.py" />（`loop_count: int = Field(ge=1)`）；迭代并行与错误模式见 <Source href={G + 'src/graphon/nodes/iteration/entities.py#L14-L18'} label="iteration/entities.py" /> 与 <Source href={G + 'src/graphon/enums.py#L93-L101'} label="ErrorStrategy / ErrorHandleMode" />。

### 洞察四：图必须无环——放弃“任意跳转”，换来可预测

graphon 在构建图时会拒绝每个作用域内的环路，重复执行只能通过“循环 / 迭代”这种容器节点表达。这是一个明确的取舍：用户不能像写代码那样随意 `goto` 回前面的节点，但换来了三个好处——每次运行步数有上限、画布上一眼能看出哪里会重复、引擎可以准确判断“某个节点是否还会被执行”（这正是并行汇合和跳过传递能成立的前提）。

<Source href={G + 'ARCHITECTURE.md#L152-L163'} label="ARCHITECTURE.md" />：“Container handlers provide repetition; each scope's edges must be acyclic.”

### 取舍与替代方案

- **得到的**：每一步可见、可单测、可回放；非工程师能改提示词和分支；运行有步数和时间上限；同一张图能导出成 YAML 复用。
- **付出的**：复杂逻辑在画布上会变得很“宽”，大图编辑卡顿（[#28245](https://github.com/langgenius/dify/issues/28245)，约 100 个节点时明显）；不能任意回跳，只能用容器节点表达重复；概念多（Chatflow / Workflow、Answer / End），新手容易混淆。
- **替代方案**：纯代码编排框架（LangGraph 一类）：表达力强、易做单元测试，但把产品和业务人员挡在门外。纯 Agent 平台：上手快，但难以给出确定的成本、延迟和审计结论。Dify 的折中是“图做骨架，代码节点和 Agent 节点作为逃生舱”。

<Callout type="要点">
- 画布的价值是**让步骤显式化**：输入、输出、出错走向都写在图上，人人能看懂、能改、能审计。
- Chatflow 服务“多轮对话的终端用户”，Workflow 服务“一次性输入输出的系统调用”，两者共用同一引擎。
- 变量池、分支跳过、汇合等待、失败分支这些概念，都在回答“下一步拿什么、走哪条路、出错怎么办”。
- “图必须无环”是有意的约束：放弃任意跳转，换来可预测的执行和可推理的状态。
</Callout>



## 二、哪些环节用固定流程，哪些交给 Agent

<Callout type="结论">Dify 的判断是“默认确定，按需自主”：能写成规则的写成节点；必须靠模型判断的地方，用输出被严格约束的“窄口径”LLM 节点；只有当**路径本身无法预先画出**时才放 Agent——而且最新的 Agent 节点也被包进了“声明输出 + 类型检查 + 失败策略”的确定性外壳里。</Callout>

### 问题背景

2024 年以前，很多团队做 AI 功能会陷入两种失败：一种是把所有逻辑塞进一个超长提示词，让模型“既分类、又抽取、又回答”，结果某一项一出错整体就崩；另一种是直接上 Agent，结果在演示里惊艳，在生产里因为路径不稳定、成本飘忽而被叫停。Dify 社区的需求也反映了这种张力：用户一边要求“在工作流里加 Agent 节点”（[#7470](https://github.com/langgenius/dify/issues/7470)，36 条评论），一边又抱怨 ReAct 模式的 Agent 经常给不出最终答案（[#19303](https://github.com/langgenius/dify/issues/19303)）。

### 产品洞察

### 洞察一：“受约束的 LLM 调用”——让模型只做一道选择题或填空题

Dify 把最常见的几类模型用法做成了专用节点，每个节点都把模型的自由度收窄到“只能回答这一类问题”，并且为“模型答歪了”预先设计了退路：

- **问题分类器**：模型只能从你定义的类别里选一个，每个类别对应一条出边。如果模型的输出解析不出合法类别，节点**不报错，而是回落到第一个类别**。产品含义：下游永远有路可走，你应该把“最安全的默认处理”放在第一个类别。
- **参数提取器**：用函数调用或提示词两种模式从文本里抽取结构化字段，并校验字段数量、必填项和类型。校验失败时节点仍然“成功”，但输出 `__is_success=0` 和 `__reason`，把“抽取失败”交给下游的条件分支决定怎么处理（比如追问用户）。
- **LLM 节点的结构化输出**：可以给出 JSON Schema（JSON 结构定义），解析失败会以明确的错误信息失败，于是可以接上重试或失败分支。

```
# 问题分类器：解析不出合法类别时，回落到第一个类别（graphon）
category_name = rendered_classes[0].name
...
if "category_name" not in result_text_json or "category_id" not in result_text_json:
    return category_name, category_id, category_label
```

### 洞察二：Agent 的位置经历了三次演进

1. <strong>Agent 应用（agent-chat）</strong>：一种独立的应用类型，支持函数调用和 ReAct（思考-行动-观察循环）两种策略，最大轮次被硬性限制在 99 以内，超出就报 `AgentMaxIterationError`。它适合“一个能调工具的聊天助手”，但无法嵌入流程。
2. **工作流里的 Agent 节点**：回应 #7470 的诉求，Agent 成为工作流中的一个节点，推理策略本身做成了插件（Agent 策略插件），可以替换。这样“流程骨架 + 某一步自主”成为可能。
3. **新一代 Agent 节点与 Agent 应用**：当前代码里出现了 `agent_v2` 节点和新的 `agent` 应用类型，由独立的 Dify Agent 运行时（`dify-agent` 与 `agent_backend` 服务）支撑。README 的描述也变成“拥有自己沙箱的自主 Agent：能执行命令、安装软件、处理文件”。

第三阶段最值得产品人注意的设计是**声明式输出**：在工作流里使用 Agent 节点时，你要先声明它必须产出哪些输出（名称、类型、是否必填），运行后系统逐个做类型检查，文件类输出还可以用模型对照“标准样例文件”做内容检查；任何一项不合格，就按这个输出配置的策略处理——重试整个 Agent、用默认值替换、走失败分支，或者直接让节点失败。多个输出失败时按“失败分支 &gt; 停止 &gt; 默认值”的优先级合并成一个决定。

换句话说，**Agent 的过程可以不确定，但它交给流程的结果必须是确定的形状**。这是 Dify 对“确定性 vs 灵活性”最清晰的一次表态。

### 洞察三：确定性 vs 灵活性，本质是在为“谁来承担不确定性”定价

| 维度 | 固定流程（含受约束 LLM 节点） | Agent |
| --- | --- | --- |
| 成本与延迟 | 可预估：节点数 × 单次调用 | 随轮次浮动，需上限兜底 |
| 可测试性 | 每个节点可单步运行，回归测试容易 | 同一输入可能走不同路径，只能做统计意义上的评估 |
| 可审计 | 日志里每一步输入输出一目了然 | 要看完整的思考与工具调用轨迹 |
| 覆盖面 | 只能处理你预见到的情况 | 能处理没预见到的组合 |
| 失败方式 | 局部失败、可设计兜底 | 可能“看起来成功但做错了” |

Dify 的产品结构等于给出了一个默认答案：**把不确定性限制在尽量小的盒子里**。分类、抽取、改写这类“模型判断一次就结束”的环节，用受约束节点；只有“需要多轮探索、步骤数事先未知”的环节才交给 Agent，并且给它轮次上限、执行时间上限和输出契约。

### 洞察四：怎么选——一个实用的判断顺序

1. 这一步**不需要**理解自然语言吗？→ 用代码、HTTP、条件分支等普通节点。
2. 需要模型，但**输出空间是有限的**（几个类别、几个字段、一段改写）？→ 用问题分类器、参数提取器、带结构化输出的 LLM 节点。
3. 需要多次调用工具，但**顺序是固定的**？→ 仍然画成流程，每次工具调用一个节点。
4. 工具调用的**顺序和次数取决于中间结果**，事先画不出来？→ 用 Agent 节点，放在流程中间，前后用固定节点做输入整理和输出校验。
5. 整个任务都是开放式的（“帮我调研并写报告”）？→ 用 Agent 应用，但要给出轮次与时间上限，并接受结果需要人审。

<Callout type="建议">以上顺序是根据 Dify 的节点设计整理出的使用建议，并非官方文档原文。</Callout>

### 取舍与替代方案

- **得到的**：大多数业务场景可以只用受约束节点完成，成本与行为可预期；Agent 被关进节点里，失败可以像普通节点一样走兜底。
- **付出的**：新一代 Agent 依赖额外的后端服务，自部署用户在 1.15.0 遇到“标准 Docker 部署里 Agent 节点完全不可用”（[#39161](https://github.com/langgenius/dify/issues/39161)）；旧版 ReAct 对模型输出格式敏感，容易给不出最终答案（[#19303](https://github.com/langgenius/dify/issues/19303)）。
- **替代方案**：“一个大 Agent 搞定一切”的架构更省搭建时间；“完全规则化”更省钱。Dify 选择同时提供两端，并用节点契约把它们接起来，代价是用户必须学会判断用哪种。

<Callout type="要点">
- 问题分类器、参数提取器、结构化输出是“让模型做选择题”的工具，各自带有不报错的退路。
- Agent 从独立应用 → 工作流节点 → 带声明输出与失败策略的节点，方向是“过程自主、结果受控”。
- 判断标准不是“任务难不难”，而是“路径能不能预先画出来”。
</Callout>



## 三、各组件怎么分层：RAG、模型、工具

<Callout type="结论">Dify 按“谁负责、多久变一次”来切层：应用编排归业务团队，知识库和工具归数据与集成团队，模型、向量库、追踪平台这些外部依赖通过插件和供应商接口接入，基础设施归运维。每一层都可以单独替换，而不必改动上一层。</Callout>

### 问题背景

AI 应用的依赖变化极快：模型每个月都有新的，向量数据库有几十种，企业内部系统各不相同。如果工作流里直接写死“调用某家的某个模型”“查询某个向量库”，每次换供应商都要改所有应用。Dify 的分层就是在回答：**什么东西应该在工作流里配置，什么东西应该在工作区里统一管理，什么东西应该交给插件生态**。

### 产品洞察

### 洞察一：知识库被拆成“入库”和“检索”两半，入库也变成了工作流

一个知识库的生命周期分两段：

- **入库**：抽取（PDF、Word、网页、Notion 等）→ 清洗 → **分段**（通用段落、父子分段、问答对三种索引方式）→ 向量化 → 写入向量库。新版本把这一段做成了<strong>知识流水线（RAG Pipeline）</strong>：用和工作流同样的画布，组合“数据源节点 → 处理节点 → 知识库写入节点”，于是不同类型的文档可以有不同的处理流程。
- **检索**：语义检索、全文检索、混合检索、关键词检索四种方式；**重排**可以用专门的重排模型，也可以用“语义与关键词加权打分”；还可以按元数据过滤（关闭 / 自动 / 手动）。

拆开的好处是：数据团队负责“入库质量”，应用团队只在知识检索节点里选“查哪个库、怎么查”。代价是两边的问题容易互相甩锅——第 5 章的 [#29750](https://github.com/langgenius/dify/issues/29750) 就是“知识库测试面板能检索到，工作流里却检索为空”。

### 洞察二：模型供应商是“工作区级的配置”，应用只引用名字

在 Dify 里，API 密钥和模型凭据配置在工作区（租户）层面，工作流里的 LLM 节点只引用“供应商 + 模型名”。从 1.0 开始，模型供应商本身也变成了插件，由独立的插件守护进程（plugin daemon）运行。好处显而易见：

- 换模型不用改流程，只改节点下拉框；企业可以统一管理、轮换密钥。
- 新模型上线不必等 Dify 发版，插件作者就能发布。
- 发布工作流时会校验凭据策略（插件管理启用时），避免“草稿能跑、发布后没权限”。

代价是多了一个独立运行的组件。1.0.0 刚发布时，大量自部署用户遇到“无法配置模型密钥”（[#14603](https://github.com/langgenius/dify/issues/14603)，74 条评论），根源在插件守护进程安装依赖超时或网络受限。

### 洞察三：工具有七种来源，但对工作流来说都是“一个工具节点”

工具供应商类型枚举列出了七种来源：**内置工具**、**自定义 API**（导入 OpenAPI 描述即可）、**工作流即工具**（把一个已发布的工作流包装成工具）、**应用**、**知识库检索**、**MCP**（模型上下文协议，一种连接外部工具的开放标准）、**插件**。无论来源，在画布上都是同一种工具节点，在 Agent 里都是同一种可调用工具。

MCP 是社区呼声最高的需求之一（[#11415](https://github.com/langgenius/dify/issues/11415)，64 条评论，2025 年 7 月经 PR #20716 关闭）。现在 Dify 是**双向**的：既能作为客户端调用 MCP 服务器上的工具，也能把自己的应用发布成 MCP 服务器给别的 AI 客户端调用。

“工作流即工具”让复杂能力可以被封装、复用、嵌套，但也带来了递归风险，所以有嵌套调用深度上限（默认 5 层）。

### 洞察四：对开发者和企业用户，同一套分层意味着不同的东西

- **对开发者**：扩展点清晰：要接新模型写模型插件，要接内部系统写自定义 API 或 MCP，要加复杂逻辑写代码节点；不必理解整个平台。
- **对企业用户**：凭据集中管理、角色分级、可以只打包需要的向量库和追踪组件（构建时用 `--no-group vdb-all` 排除默认组件，官方说法是“增强发行版的安全性与灵活性”）；但离线环境装插件困难（[#14848](https://github.com/langgenius/dify/issues/14848)）。
- **对平台自身**：30 种向量库、8 个追踪平台以独立包形式存在，Dify 核心不必为每个供应商背负代码；但组合爆炸让测试和升级更难（[#27291](https://github.com/langgenius/dify/issues/27291) 就是一次向量库客户端升级引发的事故）。

### 取舍与替代方案

- **得到的**：换模型、换向量库、换追踪平台都不动应用；生态可以独立于主仓库发布能力。
- **付出的**：部署组件多（标准编排里有 api、worker、web、sandbox、plugin_daemon、ssrf_proxy、agent_backend 以及向量库等），任何一个配置不对都会表现为“上层功能不可用”。
- **替代方案**：把模型和工具都做成核心代码的一部分（早期 Dify 就是这样）：部署简单，但每个新供应商都要等主仓库发版，且核心代码越来越臃肿。1.0 的插件化是用部署复杂度换生态速度。

<Callout type="要点">
- 知识库拆成“入库流水线”和“检索节点”两半，入库本身也能编排。
- 模型和凭据在工作区层面管理，应用只引用名字；模型供应商自 1.0 起是插件。
- 七种工具来源统一成一个工具节点，MCP 双向支持，工作流本身也能变成工具。
- 分层带来可替换性，也带来部署与升级的复杂度，这正是第 5 章大量痛点的来源。
</Callout>



## 四、原型怎么走向生产

<Callout type="结论">一个在画布上“能跑通”的工作流，离“敢让客户用”还差五类东西：**可调试、可版本化、可交付、可观测、可防护**。Dify 在每一类都补了专门机制，大部分是普通用户看不见、但运维和合规团队离不开的部分。</Callout>

### 问题背景

AI 原型的典型路径是：周五下午在画布上拼出一个流程，演示效果很好；下周一接入真实流量后，各种问题冒出来——某个模型偶尔超时、一个用户的长文档把上下文撑爆、有人改了提示词导致线上回答变差却不知道是谁改的、促销日并发一高整个服务变慢。“能用”到“敢用”之间的差距，几乎都不在模型本身，而在**工程与运营机制**。

### 产品洞察

### 洞察一：调试——让每个节点都能单独跑

画布上可以**单步运行**任意节点：给它手动填入上游变量，只执行这一个节点，看输出、耗时和 token；还能查看每个节点“上一次运行”的结果。这让调提示词变成“改一下、点一下”的快循环，不必每次从头跑整个流程。

<Source href={D + 'api/services/workflow_service.py#L1154'} label="workflow_service.run_draft_workflow_node" />；控制器中还有 `get_draft_workflow_node_last_run`。

### 洞察二：草稿与发布——线上版本不会被手滑改坏

每个工作流永远有一个 `draft`（草稿）版本供编辑，发布时生成一个新的不可变版本，API 和 WebApp 只调用已发布版本。发布这一步本身就是一道闸门：会校验模型引用、凭据策略、图结构、Agent 节点配置，云版本还会做套餐检查。产品含义：<strong>“编辑”和“上线”被分成两个动作</strong>，修改有记录（可以给版本命名、写备注），也能回滚。

<Source href={D + 'api/models/workflow.py#L247'} label="Workflow.VERSION_DRAFT = &quot;draft&quot;" />；<Source href={D + 'api/services/workflow_service.py#L690-L730'} label="publish_workflow" />（`marked_name`、`marked_comment`、校验与计费检查）。

### 洞察三：交付——同一个工作流，多种出口

发布后的应用天然拥有：REST API（后端即服务）、可直接分享或嵌入网页的 WebApp、MCP 服务器入口，以及“作为工具”被其他应用调用的能力；工作流还可以由定时器、Webhook、插件事件等触发器启动。对产品团队来说，<strong>做一次，就能同时服务内部员工（WebApp）、自家系统（API）和别人的 AI 助手（MCP）</strong>。

### 洞察四：观测——日志、标注、追踪三件套

- **日志**：每次运行的每个节点输入输出、耗时、token、费用都被记录，可以按会话回看。
- **标注回复**：运营人员可以把一个“标准答案”标注到某类问题上；之后相似问题（相似度超过阈值）会直接返回标注答案，不再调用模型。这是把人工经验沉淀进系统的最低成本方式。
- **追踪集成**：支持 Langfuse、LangSmith、Opik、Arize、Phoenix、Weave、阿里云、MLflow、Databricks、腾讯云等追踪平台。追踪数据通过独立的异步队列 `ops_trace` 发送，不阻塞主流程。

<Source href={D + 'api/core/app/features/annotation_reply/annotation_reply.py#L19-L45'} label="annotation_reply.py" />（`score_threshold`）；<Source href={D + 'api/core/ops/entities/config_entity.py#L8-L18'} label="TracingProviderEnum" />；队列列表见 <Source href={D + 'api/docker/entrypoint.sh#L34-L45'} label="api/docker/entrypoint.sh" />。

### 洞察五：防护——多租户、限流、上限、沙箱、队列

- **多租户与权限**：工作区内有所有者、管理员、编辑、普通成员、知识库操作员五种角色，后者只能管理知识库，适合让数据团队维护资料却不能改应用。
- **速率限制**：每个应用可以设置最大并发请求数，超出时直接返回 “Too many requests”，保护下游模型配额。
- **执行上限**：单次运行最多 500 步、3600 秒，嵌套调用最多 5 层，单个变量最大 200 KB——防止一个配置错误的循环烧掉整月预算。
- **代码沙箱**：代码节点运行在独立的 `sandbox` 服务里，网络请求经过 `ssrf_proxy`（防服务端请求伪造的代理），并有读写超时和输出大小限制。
- **异步队列**：文档索引、知识流水线、工作流执行、追踪、邮件等走不同的 Celery 队列；云版本甚至按套餐把工作流分到 `workflow_professional`、`workflow_team`、`workflow_sandbox` 不同队列，避免免费用户的洪峰拖慢付费用户。

<Source href={D + 'api/enums/account.py#L7-L12'} label="TenantAccountRole" />；<Source href={D + 'api/core/app/features/rate_limiting/rate_limit.py#L73-L88'} label="rate_limit.py enter()" />；<Source href={D + 'api/configs/feature/__init__.py#L945-L974'} label="WorkflowConfig" />（500 步 / 3600 秒 / 深度 5 / 200KB）；<Source href={D + 'api/configs/feature/__init__.py#L120-L150'} label="CodeExecutionSandboxConfig" />；<Source href={D + 'api/docker/entrypoint.sh#L34-L45'} label="按版本划分的 Celery 队列" />。

### 取舍与替代方案

- **得到的**：大部分生产级机制开箱即用，小团队不必自建日志、限流、沙箱和版本管理。
- **付出的**：默认值未必适合你的负载：[#36023](https://github.com/langgenius/dify/issues/36023) 中 8 核 32G 的自部署环境在 20 并发时 Agent 工作流耗时到 120 秒，改环境变量也不见效；[#15500](https://github.com/langgenius/dify/issues/15500) 中运行已成功，但发布后的界面却提示“因超时未显示结果”。
- **替代方案**：把 Dify 只当原型工具，上线时用代码重写；或者只用它的 API 层，把观测接入自家平台。Dify 用十种追踪集成和完整 API 表明它希望自己就是生产环境。

<Callout type="要点">
- 单步运行 + 上次运行结果，让调试从“跑全流程”变成“点一个节点”。
- 草稿与发布分离，发布本身是一道校验闸门。
- 日志、标注、追踪组成运营闭环；角色、限流、执行上限、沙箱、队列组成防护网。
- 默认值只是起点，生产负载需要按自身情况调优。
</Callout>

### 产品洞察：把 15 个痛点归成四个主题

### 主题一：每多一个可替换的组件，就多一条升级断裂线

#27291（向量库客户端升级）、#14603（插件守护进程）、#39161（Agent 后端）、#14848（离线插件）有一个共同点：问题都出在第 3 章那些“为了可替换而拆出去”的组件上。分层让 Dify 的生态扩展得很快，但自部署用户要为每一个组件的版本兼容、网络环境、资源配额负责。**评论最多的 issue 几乎都与升级或部署有关**，这是开源自部署产品的结构性成本。

### 主题二：知识库的失败经常是“静默”的

#29750 中检索为空不报错、#20555 中检索变慢但结果没变——用户感知到的只是“回答变差了”或“变慢了”。因为检索为空在产品语义上是合法的成功状态（第 6 章会讲），所以这类问题很难被监控告警发现。

### 主题三：可视化让简单的事情变简单，也让复杂的事情暴露出新问题

#39151（并行失败归因）、#17626（分支中的流式输出）、#28245（大图卡顿）、#9741（概念混淆）都发生在用户把画布用到更复杂的程度之后。图越大，越需要“谁导致了什么”的归因、越需要性能优化、越需要清晰的概念边界。

### 主题四：Agent 的不确定性最终要靠“契约”和“替代策略”收住

#7470 推动了 Agent 进入工作流，#19303 说明依赖输出格式的 ReAct 策略很脆弱，#39161 说明新一代 Agent 的运维成本更高。Dify 的应对方向——可插拔的 Agent 策略、声明式输出、失败策略——都是在把 Agent 的不确定性关进可管理的边界。

### 取舍与替代方案

- **观察**：很多 issue 由机器人自动回复、长时间无人跟进后被标记为陈旧而关闭（如 #26877、#15500、#19303）。对一个有近两万个 issue 的项目，这是维护带宽的现实。
- **启示**：<span class="tag warn">建议</span>对自部署产品，“升级迁移脚本 + 兼容性说明 + 一键自检”可能比新功能更能减少高讨论量 issue。
- **替代方案**：只提供云服务可以规避大部分部署痛点，但会失去对数据敏感的企业客户。Dify 同时维护云版与社区版，等于承担了两份复杂度。

<Callout type="要点">
- 高讨论量痛点集中在升级、自部署、插件依赖，而不是模型能力。
- 知识库问题常常静默，需要主动监控检索质量。
- 画布用得越深，越需要失败归因、性能和概念边界方面的投入。
</Callout>



## 六、边界场景的处理逻辑

<Callout type="结论">Dify 处理异常的核心思路是：**把“出错”从意外变成可设计的路径**。容易出错的节点允许配置重试、默认值或失败分支；不该算错误的情况（检索为空）返回成功，让用户自己决定；可能失控的情况（循环、超时、并发）用全局上限兜底；停止和超时都通过同一种“中止命令”实现。</Callout>

### 问题背景

AI 应用的异常比普通软件多一类：除了网络超时、服务宕机这些“硬错误”，还有模型输出格式不对、回答太长、检索没找到、Agent 绕圈子这类“软错误”。产品上的难点是区分：哪些应该让整个流程失败？哪些应该优雅降级？哪些根本不算错误？下面 10 种场景按“用户看到什么 / 产品策略 / 证据”展开。标有“在模拟器中查看”的，可以跳回第 1 章亲眼看走向。

### 产品洞察：三条贯穿所有场景的原则

### 原则一：只给“不可靠”的节点配异常处理

前端只在 LLM、工具、HTTP 请求、代码、Agent 这几类节点上显示“异常处理”面板，重试只在前四类上提供。这几类节点的共同点是：依赖外部服务或运行用户代码，失败是常态。条件分支、模板转换这类纯逻辑节点出错通常意味着配置错误，应该在调试阶段修好，而不是在运行时兜底。

<Source href={D + 'web/app/components/workflow/utils/workflow.ts#L172-L181'} label="hasErrorHandleNode" />；<Source href={D + 'web/app/components/workflow/utils/node.ts#L169-L176'} label="hasRetryNode" />。

### 原则二：顺序是“先重试，再按策略兜底，没有策略就失败”

```
# graphon NodeFailureHandler.handle（节选）
if node.retry and retry_count < node.retry_config.max_retries:
    return self._handle_retry(event, retry_count)
match node.error_strategy:
    case None:                       return None   # 没有兜底：当前作用域失败
    case ErrorStrategy.FAIL_BRANCH:  return self._handle_fail_branch(event)
    case ErrorStrategy.DEFAULT_VALUE: return self._handle_default_value(event)
```

走失败分支或默认值时，节点状态变为“异常（exception）”而非“失败”，并把 `error_message` 和 `error_type` 作为输出变量交给下游，整次运行最终是“部分成功”。这让运营能在日志里一眼区分“彻底失败”和“降级成功”。

<Source href={G + 'src/graphon/engine/event/node_failure.py#L48-L97'} label="node_failure.py handle()" />；<Source href={G + 'src/graphon/engine/event/node_failure.py#L131-L205'} label="失败分支与默认值的输出" />；<Source href={G + 'src/graphon/enums.py#L120-L150'} label="运行状态含 partial_succeeded" />。

### 原则三：停止、超时、超步数，都是同一个“中止命令”

用户点停止、运行超过最长时间、步数超过上限，最终都会向引擎的命令通道发送一条 `AbortCommand`（中止命令）。统一机制的好处是行为一致：已完成节点的结果保留，未开始的节点不再执行。一个有意思的细节是，超限中止在 Dify 里被转换成和“用户手动停止”同一类停止事件，只是原因文字不同。

<Source href={G + 'src/graphon/engine/command/README.md#L5-L12'} label="command/README.md" />；<Source href={D + 'api/core/app/apps/workflow_app_runner.py#L649-L654'} label="workflow_app_runner.py" />：`GraphRunAbortedEvent` → `QueueStopEvent(stopped_by=USER_MANUAL, reason=...)`。

- **用户看到**：循环节点必须填最大次数（1 到 100），否则无法保存；Agent 达到最大轮次会报错；整个运行超过 500 步会被中止。
- **产品策略**：四层上限层层兜底：循环次数（前端默认上限 100）、迭代最大数量（默认 99）、Agent 轮次（硬上限 99）、全局步数（500）。产品含义：任何“可能不结束”的结构，在配置时就必须回答“最多几次”。
- **证据**：<Source href={D + 'web/app/components/workflow/nodes/loop/default.ts#L95-L101'} label="loop/default.ts" />；<Source href={D + 'docker/.env.example#L140-L150'} label=".env.example" />（LOOP_NODE_MAX_COUNT=100、MAX_ITERATIONS_NUM=99、MAX_PARALLEL_LIMIT=10）；<Source href={D + 'api/core/agent/cot_agent_runner.py#L198-L200'} label="AgentMaxIterationError" />；<Source href={G + 'src/graphon/engine/layer/builtin/execution_limits.py#L69-L97'} label="ExecutionLimitsLayer" />。

<DetailItem title="6. 并行汇合" tags={[{ label: "等谁、跳过谁、一条失败怎么办" }]}>

- **用户看到**：汇合节点（如变量聚合器）会等所有上游分支“有结论”后才执行；未被选中的分支显示为跳过。
- **产品策略**：规则很简洁：一个节点的入边里**没有“未确定”的边，并且至少有一条被走过**，它才就绪；分支选中一条后，其它出边标记为跳过，并沿下游传递——所有入边都被跳过的节点也被跳过。并行中某一支失败且无兜底时，整个作用域快速失败，而这正是 #39151 中“其他节点状态无人认领”的来源。迭代的并行度默认 10。

### 取舍与替代方案

- **得到的**：异常处理是“配置”而不是“代码”，产品和运营也能设计降级体验；全局上限让最坏情况可预期。
- **付出的**：默认没有兜底（失败策略默认为空、重试默认关闭），新手的第一个上线版本往往一出错就整体失败；“检索为空算成功”需要用户自觉加判断。
- **替代方案**：默认给所有节点开重试和兜底：新手更友好，但会掩盖配置错误、让账单在故障时翻倍。Dify 选择“默认暴露错误、按需兜底”。

<Callout type="要点">
- 只有外部依赖类节点有异常处理：先重试，再失败分支或默认值，最后才是失败。
- 检索为空是成功，判断交给用户；路由节点永不卡死，抽取节点把失败交给下游。
- 停止、超时、超步数统一成中止命令；执行上限在节点完成时检查，长节点要靠自身超时。
</Callout>



## 七、AI 功能如何真正落地

<Callout type="结论">Dify 的代码和 issue 共同说明一件事：AI 功能落地的难点，大部分不在“模型会不会”，而在**把不确定性关进可管理的盒子、让每一步可见、给每种失败一条出路、让运营能持续改进**。</Callout>

### 问题背景

前六章分别从设计、分工、分层、生产化、用户痛点、边界场景看了 Dify。如果把它当作一份“别人替你踩过的坑”的清单，可以提炼出下面这些对 AI 产品人普遍适用的启示。每条都标注了在前文中的依据。

### 产品洞察：八条启示

1. **先把流程画出来，再决定哪一步需要智能**
   Dify 的默认形态是流程图，Agent 只是其中一种节点。做 AI 功能时先列出步骤，再逐步问“这一步真的需要模型吗？需要的话，输出能不能收窄成选择题？”多数步骤的答案会让你用更便宜、更稳定的方案。（第 1、2 章）
2. **给模型的每一次调用都设计“答歪了怎么办”**
   问题分类器回落到第一个类别、参数提取器输出成功标记、结构化输出失败可走失败分支——它们都在回答同一个问题。没有退路的模型调用，迟早成为线上事故。（第 2、6 章）
3. **让 Agent 过程自由，结果受约束**
   新一代 Agent 节点要求声明输出、做类型检查、配置失败策略。即使你没用 Dify，也可以照做：Agent 交给下游的东西必须有固定形状，并且有人能判断它合不合格。（第 2 章）
4. **区分“错误”和“空结果”，并让空结果可被看见**
   检索为空是合法结果，但它也是回答质量下降的头号信号。#29750 说明静默的空结果最难发现：建议在流程里显式处理，并把空检索率当作监控指标。（第 5、6 章，监控部分为 <span class="tag warn">建议</span>）
5. **任何可能不结束的东西，都要在配置时回答“最多几次、最长多久”**
   循环次数、迭代数、Agent 轮次、全局步数、全局时长、嵌套深度，Dify 设了六层上限。注意上限的检查时机：在节点完成时检查，就拦不住一个卡死的节点。（第 4、6 章）
6. **编辑和上线必须是两个动作**
   草稿与发布分离、发布时校验、版本可命名可回滚。AI 功能的“代码”常常是提示词，改提示词也要走发布流程。（第 4 章）
7. **可替换性有价格，升级路径是产品的一部分**
   插件化、供应商化让生态飞速扩张，但评论最多的 issue 几乎都来自升级和部署。如果你的产品允许客户自部署，迁移脚本、兼容说明和自检工具要和新功能一起排期。（第 3、5 章）
8. **把人的经验沉淀成系统的一部分**
   标注回复让运营直接修正高频问题的答案，日志与追踪让每次失败都能被复盘。AI 功能上线不是终点，“运营闭环”决定它三个月后是变好还是变差。（第 4 章）

### 具体例子：用这些启示重看第 1 章的客服流程

- 知识检索后加“结果为空？”判断——对应启示 4。
- 问题分类器的第一个类别放“其他 / 转人工”这种最安全的处理——对应启示 2。
- 售后办理才交给 Agent，并限制轮次、声明输出“工单号”——对应启示 1、3、5。
- LLM 节点开启重试，并配置失败分支到兜底话术——对应启示 2。
- 上线走发布流程，接入追踪平台，高频问题用标注回复——对应启示 6、8。

### 取舍与替代方案

- **Dify 路线适合**：需要多角色协作、需要审计、流程大体稳定、希望一次搭建多渠道交付的团队。
- **可能不适合**：极度定制的交互、对延迟极端敏感、或流程本身就是开放式探索的场景；以及无法承担多组件运维的小团队自部署。
- **可借鉴而不必照搬**：即使最终用代码实现，也可以借用 Dify 的产品原则：显式步骤、窄口径模型调用、失败分支、全局上限、草稿与发布、标注闭环。

<Callout type="要点">
- 落地难点主要在工程与运营机制，而不在模型能力。
- “默认确定，按需自主”是一个可复用的产品原则。
- 为每种失败设计出路，为每个循环设置上限，为每次修改设置发布流程。
</Callout>
