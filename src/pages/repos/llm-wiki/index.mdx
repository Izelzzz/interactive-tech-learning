## 一、它不是传统 App，而是一套思路

<Callout type="结论">LLM Wiki 交付的不是软件，而是一份“思路文件”：它描述原料、维基、规范三层结构和摄入、查询、检查三种操作，具体实现交给你的 agent 去搭。</Callout>

### 问题背景：为什么聊天记录和收藏夹沉淀不成知识

大多数人用 LLM 处理资料的方式是：上传一批文件，提问，得到一个答案。答案很好，但用完就散了。下次换个角度再问，LLM 又要从原始文件里重新找、重新拼。收藏夹也是一样，存进去的是原料，不是理解。

Karpathy 在原文开头就点出了这个问题：在常见的做法里，LLM 每次提问都在“从零重新发现知识”，没有积累；一个需要综合五份文档的问题，每次都得重新找碎片、重新拼起来 <Source href={G} label="原文" />。

### 洞察一：它是一份写给 agent 的“想法文件”

这份 gist 的第一段就说明了自己的身份：这是一个“想法文件”，设计出来是让你复制粘贴给自己的 LLM agent（原文举了 OpenAI Codex、Claude Code、OpenCode 等例子）。它只负责传达高层思路，具体细节由你的 agent 和你一起搭出来 <Source href={G} label="原文" />。

结尾又强调了一次：文档是故意写得抽象的，目录结构、规范约定、页面格式、工具链都取决于你的领域和偏好；它唯一的任务就是“传达这个模式”，剩下的“你的 LLM 能想明白” <Source href={G} label="原文" />。

这本身就是一个产品形态上的信号：**产品的交付物从“一个能装的软件”变成了“一份能被 agent 执行的说明”**。第四章会专门讨论这一点。

### 洞察二：三层结构，各有主人

原文把系统分成三层 <Source href={G} label="原文" />：

| 层 | 放什么 | 谁写 | 关键约束 |
| --- | --- | --- | --- |
| 原料层（raw sources） | 文章、论文、图片、数据文件 | 你挑选放入 | **不可变**：LLM 只读不改，是唯一的事实来源 |
| 维基层（the wiki） | 摘要页、实体页、概念页、对比、总览、综述 | LLM 全权负责 | 你读，LLM 写；新原料来了它负责更新和保持一致 |
| 规范层（the schema） | 一份说明文件，如 CLAUDE.md 或 AGENTS.md | 你和 LLM 一起迭代 | 规定维基的结构、约定和工作流程，是“最关键的配置文件” |

人和 LLM 的分工也很清楚：原文说你几乎不用自己写维基，你负责挑原料、探索和提出好问题；总结、交叉引用、归档、记账这些“苦活”都由 LLM 来做。Karpathy 自己的用法是一边开着 agent、一边开着 Obsidian（一个本地 Markdown 笔记软件），他的比喻是：“Obsidian 是 IDE，LLM 是程序员，维基是代码库” <Source href={G} label="原文" />。

### 洞察三：人和 LLM 的分工，按“谁不怕麻烦”来切

原文“为什么这样可行”一节给出了整套设计的根本理由：维护知识库最累的不是阅读和思考，而是**记账**——更新交叉引用、保持摘要最新、记下新数据和旧结论的矛盾、在几十个页面之间保持一致。人之所以放弃维基，是因为维护负担增长得比价值快；而 LLM 不会厌烦、不会忘记更新某个引用，一次能改 15 个文件，**维护成本几乎为零，所以维基能一直被维护下去** <Source href={G} label="原文" />。

原文还把它和 1945 年 Vannevar Bush 设想的 Memex（一种带“联想路径”的个人知识库）联系起来：Bush 没解决的问题是“谁来做维护”，现在 LLM 来做 <Source href={G} label="原文" />。

### 例子：同一个人，两种做法

- **旧做法**：读了二十篇关于某个主题的文章，存在收藏夹里。三个月后想写一篇综述，重新打开二十个链接，一边读一边记，花一个周末。
- **LLM Wiki 的做法**：每读一篇就丢进 raw/，让 agent 摄入。三个月后维基里已经有这个主题的概念页、各篇文章的摘要页、彼此矛盾的地方被标出来的段落。写综述时，你从维基出发，而不是从原料出发。

### 取舍与替代方案

- **为什么不直接做成一个 App？** 因为每个人的领域、偏好和工具都不同。原文明确说“一切都是可选的、模块化的”：只有文字原料就不需要图片处理，规模小就不需要搜索引擎 <Source href={G} label="原文" />。做成 App 就得替所有人做这些选择。
- **代价**：用户需要一个能读写文件的 agent，也要愿意和 agent 一起把规范调出来。对不熟悉命令行和 agent 的人，门槛比装一个 App 高。社区实现就在填这个空白：比如中文社区版提供了一键安装到 Claude Code、Codex 等工具的脚本，还在开发一个本地的“工作台”界面 <Source href={SK} label="README" />。

<Callout type="要点">
- 它是一份思路文件，不是软件；实现交给你的 agent。
- 三层：原料层不可变、维基层归 LLM、规范层由人和 LLM 共同迭代。
- 分工的依据是“谁不怕麻烦”：记账交给 LLM，挑选和判断留给人。
</Callout>

## 二、思维一：RAG 不等于知识管理

<Callout type="结论">检索增强（RAG）解决的是“这次怎么答好”，知识管理要解决的是“下一次从哪里开始”。LLM Wiki 把综合工作提前到摄入时做一次，并且一直保持更新，而不是每次提问都重做。</Callout>

### 问题背景：检索每次都从零开始

RAG（检索增强生成）的流程是：提问时，从原始文档里检索出相关片段，交给模型生成答案。原文说这种做法“能用”，但 LLM 在每个问题上都在重新发现知识，**没有任何东西被积累下来**；NotebookLM、ChatGPT 的文件上传和大多数 RAG 系统都是这样 <Source href={G} label="原文" />。

### 洞察一：把“综合”从查询时挪到摄入时

LLM Wiki 的关键区别是：新原料进来时，LLM 不只是给它建索引等着以后检索，而是读它、提取要点、**把它整合进已有的维基**——更新实体页、修订主题摘要、标出新数据和旧结论的矛盾、加强或挑战正在形成的综合结论。原文的说法是：知识“编译一次，然后保持最新”，而不是每次查询都重新推导 <Source href={G} label="原文" />。

这就像编程语言里“解释执行”和“编译执行”的区别：解释器每次运行都要重新理解源代码，编译器把理解的结果存成产物，之后直接用。

### 洞察二：积累的是“关系”，不只是内容

原文用一句话概括了维基的价值：它是一个**持久的、会复利增长的产物**。交叉引用已经建好了，矛盾已经被标出来了，综合结论已经反映了你读过的所有东西 <Source href={G} label="原文" />。

RAG 检索出来的是孤立的片段，片段之间的关系要在每次回答时临时推断；维基里，关系本身就是被保存下来的知识。这也是 Bush 设想 Memex 时最看重的部分：文档之间的联系和文档本身一样有价值。

除了钱，还有几个维度的差别：

| 维度 | 每次检索（RAG） | 编译成维基 |
| --- | --- | --- |
| 一致性 | 同一个问题换个问法，可能检索到不同片段，答案不同 | 结论写在页面上，每次读的是同一份 |
| 可读性 | 只能通过提问来看到知识 | 人可以直接浏览、跟链接、看图谱 |
| 可审阅 | 答案里的推理过程用完即弃 | 每次修改都在文件里，可以用 git 查看差异和历史 |
| 矛盾处理 | 矛盾的片段可能被一起检索出来，模型临时取舍 | 摄入时就标出矛盾，留下记录 |
| 上下文利用 | 塞进去的是原始片段，信息密度低 | 塞进去的是整理过的页面，信息密度高 |

### 例子：读一本书

原文举的一个场景是读书：每读一章就摄入一章，为人物、主题、情节线建页面，记录它们之间的联系。读完整本书，你就有了一个丰富的“伴读维基”，像 Tolkien Gateway 那样由志愿者多年建成的托尔金粉丝维基，只是这次由 LLM 帮你一个人建出来 <Source href={G} label="原文" />。如果用 RAG，读完之后你有的只是一本书和一个能回答问题的搜索框。

### 取舍：什么时候仍然需要检索

编译不是检索的替代品，两者是叠加的：

- **规模变大时**：原文说索引文件在中等规模下够用，再大就需要一个真正的搜索工具 <Source href={G} label="原文" />。社区的命令行实现已经加上了分块向量检索和关键词重排，用来在大维基里先缩小范围 <Source href={LC + '#L366-L373'} label="README" />。
- **资料频繁变动时**：如果原料每天大量更新、而且大多只会被问一次（比如客服工单），提前编译的收益很低。
- **一次性的问题**：只问一次的事，直接检索更省事。

<Callout type="要点">
- RAG 是“每次现做”，LLM Wiki 是“提前做好并保持更新”。
- 积累下来的不只是内容，还有交叉引用、矛盾标记这些关系。
- 两者不是二选一：规模大了，维基上面再叠一层搜索。
</Callout>

## 三、思维二：File over App

<Callout type="结论">知识保存在普通的 Markdown 文件和文件夹里，而不是锁在某个应用的数据库里。这样任何工具、任何 agent 都能读写，也能用 git 管版本，换工具时知识不会被困住。</Callout>

### 问题背景：知识被锁在应用里

很多笔记和知识管理产品把内容存在自己的数据库或私有格式里。导出往往有损失，换产品等于搬家，而且你的 AI 助手要读这些内容，还得通过这个产品提供的接口。

### 洞察一：文件是 agent 最熟悉的接口

LLM Wiki 的维基层就是“一个装着 LLM 生成的 Markdown 文件的目录” <Source href={G} label="原文" />。今天的编码 agent（Claude Code、Codex 等）天生就会读文件、写文件、搜索文件、跑命令。不需要为它们专门做集成，文件夹本身就是接口。

同一份维基可以同时被多个工具使用：agent 写，Obsidian 读和画图谱，git 管历史，搜索工具建索引。中文社区版也是这样做的：它的技能形态和工作台形态“读写同一份知识库格式” <Source href={SK} label="README" />。

### 洞察二：git 免费送你版本历史和审阅

原文提醒：维基就是一个 Markdown 文件的 git 仓库，版本历史、分支和协作都是免费得到的 <Source href={G} label="原文" />。

这对“让 LLM 写知识”特别重要：LLM 改了什么，`git diff` 一目了然；改坏了可以回退；团队使用时可以走合并请求让人审阅。原文在团队场景里也提到了“可能需要人在环中审阅更新” <Source href={G} label="原文" />。

### 洞察三：用约定弥补“文件没有结构”

文件的弱点是缺少数据库那样的结构化查询。LLM Wiki 和社区实现用约定来弥补：

- **YAML 头信息**：原文建议让 LLM 给页面加上标签、日期、来源数这类元数据，再用 Obsidian 的 Dataview 插件生成动态表格 <Source href={G} label="原文" />。
- **固定格式的日志**：日志每条以固定前缀开头，用 grep 就能解析 <Source href={G} label="原文" />。
- **命名和路径约定**：例如 Astro-Han 的实现规定原料保存为“raw/主题/日期-描述.md”，维基页面只允许一层主题目录 <Source href={AH + '#L14-L22'} label="SKILL.md" />。

### 例子：换工具不搬家

假设你今天用 Claude Code 维护维基、用 Obsidian 阅读，明年换成别的 agent 和别的阅读器。因为一切都是 Markdown 文件，新 agent 读一遍规范文件就能接手，新阅读器打开文件夹就能用。知识没有被任何一家的产品锁住。

### 取舍与替代方案

| 文件优先的代价 | 社区的补救 |
| --- | --- |
| 没有结构化查询 | 头信息加 Dataview；或者像 llm-wiki-compiler 那样另存一份状态文件记录来源哈希和归属关系 <Source href={LC + '#L270-L280'} label="README" /> |
| 多人或多个 agent 同时写会冲突 | 用 git 分支和合并；Astro-Han 的实现要求多份原料可以并行搜集，但编译必须一份一份来，因为索引、日志和级联更新是共享状态 <Source href={AH + '#L122-L130'} label="SKILL.md" /> |
| 没有权限控制 | 依赖文件系统和 git 托管平台的权限；中文社区版专门写了隐私边界：文件在本机，但让 agent 处理内容时，相关片段会发给模型服务 <Source href={SK} label="README" /> |
| 界面不如专门的 App 好看 | 用 Obsidian 这类阅读器；社区也在做专门的可视化界面，如 llm-wiki-compiler 的网页查看器、中文社区版的交互式知识图谱 |

<Callout type="要点">
- 文件夹就是 agent 的通用接口，任何工具都能参与。
- git 让 LLM 的每次修改都可审阅、可回退。
- 文件的短板用约定补：头信息、日志前缀、命名规则。
</Callout>

## 四、思维三：从“提供功能”到“提供规范”

<Callout type="结论">在 agent 能自己写代码、改文件的世界里，产品可以只交付一份规范：目录约定、页面模板、操作步骤和检查清单。实现交给用户自己的 agent，而且可以按用户的需要定制。</Callout>

### 问题背景：功能越做越多，却永远不贴合每个人

传统产品的思路是把功能做进软件：导入、标签、搜索、图谱……每加一个功能都要设计、开发、维护，而且永远有用户说“我想要的不太一样”。

### 洞察一：LLM Wiki 本身就是一份规范

回到第一章的那句话：这份 gist 是一个“想法文件”，交给你的 agent，由 agent 和你一起把细节搭出来 <Source href={G} label="原文" />。Karpathy 没有发布一个 App，而是发布了一份说明，**每个读到它的人，都能让自己的 agent 实现一个只属于自己的版本**。

规范层（CLAUDE.md、AGENTS.md）在原文里的地位也说明了这一点：它是“最关键的配置文件”，决定了 LLM 是一个守纪律的维护者还是一个普通的聊天机器人 <Source href={G} label="原文" />。

### 洞察二：规范要写到“可执行、可检查”的程度

想法文件可以抽象，但用户最终放进项目里的规范必须具体。社区实现展示了一份好规范长什么样，Astro-Han 的技能说明是一个很好的例子：

- **不变量**：维基里每一个“承重”的事实（数字、日期、直接引用）都必须原样出现在它链接的原料里；编译时“先定位再写”，检查时用脚本核对 <Source href={AH + '#L39-L43'} label="SKILL.md" />。
- **分诊**：摄入前先搜索维基，判断这份原料是“新的”“更新已有内容”“有争议”还是“没有新东西”；没有新东西就只记日志，不硬写文章 <Source href={AH + '#L64-L73'} label="SKILL.md" />。
- **不改写历史**：新原料推翻旧结论时，旧结论保留，加上“已过时”或“有争议”的状态标记，绝不悄悄改写 <Source href={AH + '#L92-L98'} label="SKILL.md" />。
- **分级的检查权限**：索引不一致、断链这类“安全问题”自动修；事实核对只报告不修；矛盾、过时这类“判断问题”只报告，交给人决定 <Source href={AH + '#L164-L210'} label="SKILL.md" />。

这些规则的共同点是：**每一条都能被 agent 执行，也能被检查**。这正是规范和“愿景描述”的区别。

### 洞察三：同一份思路，两种产品形态

社区里出现了两种截然不同的实现，正好对照“功能”和“规范”：

| | 规范形态（技能说明） | 功能形态（命令行工具） |
| --- | --- | --- |
| 例子 | Astro-Han 的 karpathy-llm-wiki、中文社区版的技能形态 | atomicmemory 的 llm-wiki-compiler |
| 交付物 | 一份 SKILL.md 加模板和少量检查脚本 | 一个 npm 包，有 compile、lint、refresh、rm 等命令 <Source href={LC + '#L218-L234'} label="README" /> |
| 谁执行 | 用户自己的 agent | 工具自己调用模型 |
| 优点 | 轻、可定制、跟着 agent 一起变强 | 行为确定、可以做增量编译、内容哈希、审阅队列、质量门禁 <Source href={LC + '#L353-L362'} label="README" /> |
| 代价 | 结果依赖 agent 的能力和自觉，同样的规范不同 agent 执行得不一样 | 更重，定制要改代码或配置 |

<Callout type="推测">两种形态很可能会融合：规范负责“做什么、守什么规矩”，少量工具负责“必须确定执行的部分”（比如事实核对脚本、哈希比对）。Astro-Han 的实现已经是这样：大部分是规范，只把事实核对做成了脚本 <Source href={AH + '#L193-L200'} label="SKILL.md" />。</Callout>

## 五、重点：知识如何被编译和积累

<Callout type="结论">编译不是一次性的整理，而是一个循环：每份新原料都要经过分诊、写入、级联更新、记账；每个好问题的答案都可以回写；定期体检把矛盾、过时和断链找出来。积累来自这个循环一直在转。</Callout>

### 问题背景：“整理一次”为什么不够

很多人做过“把资料整理成笔记”这件事，但笔记会过时、会和新资料矛盾、会越来越难找。真正的难点不是第一次整理，而是**之后的每一次更新都要牵动已有的内容**。原文说一份新原料可能会触及 10 到 15 个维基页面 <Source href={G} label="原文" />，这正是人做不下去、LLM 却可以一直做的部分。

### 机制：四个环节

**1. 摄入：先分诊，再写入。** 原文描述的摄入流程是：读原料、和你讨论要点、写摘要页、更新索引、更新相关的实体页和概念页、追加日志 <Source href={G} label="原文" />。社区实现在写入前加了一步分诊，先判断这份原料属于新内容、更新、有争议还是没有新东西 <Source href={AH + '#L64-L73'} label="SKILL.md" />。分诊的产品价值是**防止维基被稀释**：不是每份原料都值得一篇新文章。

**2. 级联更新：找出所有被影响的页面。** 写完主页面后，还要检查“涟漪效应”。社区实现特别强调不能只看索引，要用关键实体和别名全文搜索整个维基，更新每一个实质受影响的页面 <Source href={AH + '#L92-L98'} label="SKILL.md" />。

**3. 查询与回写：让探索也成为积累。** 原文最重要的洞察之一是：好的答案可以作为新页面回写进维基。你要的一张对比表、一次分析、一个新发现的联系，都不应该消失在聊天记录里 <Source href={G} label="原文" />。社区实现把它做成了明确的“归档”操作：只有你说要保存时才写，而且总是新建页面、不合并进已有文章，因为答案是综合结论而不是原料 <Source href={AH + '#L146-L162'} label="SKILL.md" />。

**4. 检查：定期体检。** 原文列出的检查项包括：页面间的矛盾、被新原料推翻的过时结论、没有入链的孤立页、被提到却没有自己页面的重要概念、缺失的交叉引用、可以通过搜索补上的数据空白 <Source href={G} label="原文" />。

### 洞察：积累的三个来源

从模拟器里能看到，维基变“厚”有三条路，各自对应一个产品决策：

1. **原料的摄入**：最直接的积累。关键决策是“分诊”，宁可不写，也不要稀释维基。
2. **问答的回写**：把探索过程变成资产。关键决策是“由谁决定存不存”：原文的态度是好答案应该存 <Source href={G} label="原文" />，社区实现选择只在用户明确要求时才存 <Source href={AH + '#L146-L148'} label="SKILL.md" />，避免维基被大量一次性的答案填满。
3. **体检发现的空白**：缺页的概念、可以补的数据，会变成下一轮要找的原料和要问的问题。原文说 LLM 很擅长建议新的问题和新的原料 <Source href={G} label="原文" />。

### 取舍：一份一份来，还是批量处理

原文说 Karpathy 自己更喜欢一次只摄入一份原料，并且全程参与：读摘要、检查更新、告诉 LLM 重点在哪；但你也可以批量摄入、少一些监督，关键是把你的工作方式写进规范 <Source href={G} label="原文" />。

| | 一份一份、人在环中 | 批量、少监督 |
| --- | --- | --- |
| 质量 | 高：每次更新都被人看过 | 依赖规范和检查的严格程度 |
| 速度 | 慢 | 快 |
| 适合 | 研究、读书、个人知识 | 团队文档、大量历史资料的首次导入 |

## 六、与第二大脑、上下文工程的关系

<Callout type="结论">编译好的维基是一份“预先做好的上下文”：给 agent 读几页整理过的维基，比塞给它一堆原始片段更准、更省。上下文工程的重点从“检索什么”转向“提前沉淀什么”。</Callout>

### 问题背景：上下文窗口是稀缺资源

上下文工程（Context Engineering）关心的是：在一次模型调用里，放进上下文窗口的应该是什么。窗口有限、成本按 token 计，放进去的信息密度越高，模型表现越好。

第二大脑（Second Brain）是个人知识管理领域的概念：把你读到的、想到的东西沉淀在外部系统里，让它替你记住。过去的第二大脑主要是给人用的；LLM Wiki 让它同时成为给 agent 用的上下文来源。

### 洞察一：维基是分层的上下文

LLM Wiki 天然有一个由粗到细的结构：

1. **索引**：几十到几百行，每页一句话。原文说查询时 LLM 先读索引找页面，再深入阅读 <Source href={G} label="原文" />。
2. **概念页和摘要页**：整理过的结论和关系。
3. **原料**：只有在需要核对原话时才回去读。

这和人查资料的方式一样：先看目录，再看章节，最后才翻原文。**控制上下文大小的方法，就是只按需往下走一层。**

### 洞察二：日志是 agent 的短期记忆

agent 每次启动都是“失忆”的。原文说日志能帮 LLM 了解最近做过什么 <Source href={G} label="原文" />：新会话开始时读一下最近几条日志，就知道上次摄入了什么、问过什么、体检发现了什么。规范文件则是长期记忆：维基怎么组织、按什么规矩做事。

### 洞察三：维基让多个 agent 共享上下文

因为一切都是文件，同一份维基可以被不同的 agent 读：写代码的 agent、写报告的 agent、做研究的 agent 都可以从同一个地方获得背景知识。原文里的团队场景就是这样：用 Slack 讨论、会议记录、项目文档、客户电话喂给一个由 LLM 维护的内部维基 <Source href={G} label="原文" />。

### 例子：给编码 agent 的背景知识

假设你的项目维基里有“系统架构”“部署流程”“已知坑”几页。让编码 agent 修一个 bug 时，告诉它“先读 wiki/index.md 和相关页面”，它就能带着整理好的背景开始工作，而不是在几十个原始文档和聊天记录里乱翻。

### 取舍与替代方案

- **维基太大时**：索引本身也会超出窗口。原文的建议是规模变大后加一个搜索工具 <Source href={G} label="原文" />。社区的命令行工具用分块向量加关键词重排来缩小范围 <Source href={LC + '#L366-L373'} label="README" />。
- **维基会过时**：预先做好的上下文如果没人维护，就会变成错误的上下文。所以第五章的体检不是可有可无的。

<Callout type="推测">我们认为一个值得关注的趋势是：知识库的“读者”从人变成了“人和 agent”，页面格式会因此改变，例如更多结构化头信息、更短的摘要句、更明确的来源链接，因为这些对 agent 特别有用。</Callout>

<Callout type="要点">
- 维基是分层的上下文：索引 → 页面 → 原料，按需往下读。
- 规范是长期记忆，日志是短期记忆。
- 文件形式让多个 agent 共享同一份背景知识。
</Callout>

## 七、边界场景的处理逻辑

<Callout type="结论">编译式知识库最怕的不是“没有知识”，而是“错误的知识被当成正确的知识”。所有边界场景的处理都围绕三个原则：可追溯到来源、不悄悄改写、判断交给人。</Callout>

### 问题背景

一旦由 LLM 来写知识，就会出现人工维护时不常见的问题：它可能写进没有来源的内容，可能在批量处理时把重复概念拆成两页，也可能在原料被删除后留下没人发现的“孤儿结论”。

### 场景与对策

| 场景 | 用户会遇到什么 | 处理思路 | 依据 |
| --- | --- | --- | --- |
| 原料互相矛盾 | 两个来源说法不同 | 两种说法都保留，标“有争议”，双向链接，交给人判断 | 原文要求标出新旧矛盾 <Source href={G} label="原文" />；社区实现的状态标记 <Source href={AH + '#L92-L98'} label="SKILL.md" /> |

### 三条贯穿的原则

1. **可追溯**：每个结论都能顺着链接找到原料。这是检查能做下去的前提。
2. **不悄悄改写**：新旧冲突时留下记录，而不是用新的覆盖旧的。知识的演变本身也是知识。
3. **机械的自动做，判断的交给人**：断链、索引这类问题让 LLM 自己修；事实、矛盾、要不要建新页，交给人决定。

<Callout type="建议">如果你要把这个思路用在团队里，优先把“可追溯”做成硬规则，并让关键修改走审阅。个人使用时可以放松，但至少保留日志和 git 历史，出问题时能找回来。</Callout>

### 给做产品的人的启发

- **产品交付物可以是一份规范**：当用户都有能读写文件的 agent 时，“说明怎么做”可能比“替用户做好”更有价值，也更容易定制。
- **积累需要机制，不靠自觉**：分诊、级联更新、回写、体检，每一个都是让知识持续积累的机制。缺了任何一个，维基都会慢慢变成另一个没人维护的收藏夹。
- **把信任设计进流程**：来源链接、状态标记、检查分级、审阅队列，都是让人敢于相信 LLM 写的内容的设计。

<Callout type="要点">
- 最大的风险是“错误的知识被当成正确的”，对策是可追溯。
- 不悄悄改写，让知识的演变留下记录。
- 机械的事交给 LLM，判断留给人。
</Callout>
