## 第 1 章 autoresearch 在做什么

<Callout type="结论">
一句话结论：autoresearch 是一个“改一处代码 → 跑固定 5 分钟 → 看一个分数 → 变好就保留、否则回滚”的无限循环；它能成立，靠的不是 agent 有多聪明，而是 nanochat 被裁剪成了一个小、快、分数明确的“可被优化的环境”。
</Callout>

### 问题背景：研究者的时间被“等结果”吃掉了

传统的模型研究是这样一个节奏：研究者想一个点子，改代码，启动训练，等几分钟到几小时，看曲线，判断有没有用，再想下一个点子。真正需要人脑的只有“想点子”和“判断”两步，其余时间人都在等待和搬运。Karpathy 自己在 nanochat 的 README 里描述过这种手工节奏：他喜欢用一个 12 层的小模型做约 5 分钟的快速实验，“改一点代码，重跑一次，看看有没有帮助，进入一个迭代循环”（<Source href={NC + 'README.md?plain=1#L88-L106'} label="nanochat README 第 88–106 行" />）。autoresearch 做的事情，就是把这个人工循环原封不动地交给 agent，并让它在人睡觉时持续运转。

### 产品洞察一：整个产品就是一份写给 agent 的规范

autoresearch 没有界面、没有服务器、没有调度系统。它的“产品”是一份 Markdown 文件 `program.md`（给 agent 的工作说明书）。README 说得很直白：你不再像研究者那样改 Python 文件，而是在“编程” `program.md`，它为 agent 提供上下文，相当于“搭建你的自动化研究组织”（<Source href={A + 'README.md?plain=1#L121'} label="README 第 121 行" />）；还把它称为一个“超轻量的 skill（技能说明）”（<Source href={A + 'README.md?plain=1#L164'} label="第 164 行" />）。三个文件分工非常清晰：

| 文件 | 谁来改 | 产品含义 |
| --- | --- | --- |
| `prepare.py` | 谁都不改（只读） | 固定的数据、分词器和评估函数。这是“裁判”，必须独立于“选手”。 |
| `train.py` | agent | 模型、优化器、训练循环全在这一个文件里，“一切都可以动”。这是 agent 的“工作台”。 |
| `program.md` | 人 | 目标、规则、循环步骤、记录格式。这是人的“新工作台”。 |

证据：<Source href={A + 'README.md?plain=1#L125-L129'} label="README 第 125–129 行" />。

### 产品洞察二：循环的九个步骤，每一步都在回答一个产品问题

`program.md` 的核心是一段“永远循环”（LOOP FOREVER）的步骤（<Source href={A + 'program.md?plain=1#L90-L106'} label="第 90–106 行" />）。抛开技术细节，它可以读成：

1. **看当前状态**：现在在哪个分支、哪个提交上。——“从哪里出发”是明确的。
2. **提出并实施一个想法**：直接修改 `train.py`。——每轮只做一个改动，便于归因。
3. **先提交再运行**：`git commit`。——每次实验都有一个可追溯的版本号。
4. **运行实验**：输出全部重定向到日志文件，“不要让输出淹没你的上下文”。——保护 agent 的注意力。
5. **读取分数**：只用 `grep` 取出 `val_bpb`（验证集每字节比特数，越低越好）和显存峰值。——反馈被压缩成一两个数字。
6. **没有分数就是崩溃**：读最后 50 行报错，简单的错误修一下，修不好就放弃。
7. **记账**：写进 `results.tsv`（制表符分隔的结果表），而且这个文件不进 git。
8. **变好则前进**：保留这个提交，分支向前推进。
9. **持平或变差则回滚**：`git reset` 回到起点。

注意第 9 步：<strong>“相等”也算失败</strong>。这是一个很重要的产品取舍：只接受严格的进步，避免分支上堆满“好像没坏”的改动。

### 产品洞察三：nanochat 为什么是一个“可被优化的环境”

agent 循环能跑起来，前提是环境满足三个条件。autoresearch 的训练代码是 nanochat 的“单卡简化版”（<Source href={A + 'train.py#L1-L3'} label="train.py 开头注释" />：“从 nanochat 精选并简化”），这次简化恰好把三个条件都做到了：

#### 小

只有一个文件可改、一块 GPU、没有分布式和复杂配置（<Source href={A + 'README.md?plain=1#L175-L179'} label="README 设计选择" />）。agent 能把整个代码库读进上下文，人也能读懂每一次差异。完整版 nanochat 覆盖分词、预训练、微调、强化学习、推理，对 agent 来说“面”太大。

#### 能在固定预算内跑完

训练固定 5 分钟墙钟时间（`TIME_BUDGET = 300`，<Source href={A + 'prepare.py#L31'} label="prepare.py 第 31 行" />），一小时约 12 次实验，一夜约 100 次（<Source href={A + 'program.md?plain=1#L114'} label="program.md 第 114 行" />）。反馈周期从“小时”变成“分钟”，循环次数才足够多。

#### 有明确分数

唯一指标 `val_bpb`，与词表大小无关，所以改了模型结构也能公平比较（<Source href={A + 'README.md?plain=1#L131'} label="README 第 131 行" />）。验证集固定为某一个数据分片（<Source href={A + 'prepare.py#L43'} label="prepare.py 第 43 行" />）。

这三点之所以是“前提”，可以反过来想：如果一次实验要跑 8 小时，一夜只能试一次，agent 再聪明也只是一个慢速的人；如果分数需要人看样本主观判断，循环每一轮都要等人；如果代码库大到 agent 读不完，它的改动就会越来越像瞎猜。nanochat 本身就是围绕“可比较的分数”设计的：它维护一个“训练到 GPT-2 水平要多少小时”的排行榜（<Source href={NC + 'README.md?plain=1#L10-L22'} label="nanochat README 第 10–22 行" />），并且只有一个复杂度旋钮（模型深度），其他超参数都随之自动确定（<Source href={NC + 'README.md?plain=1#L108'} label="第 108 行" />）。一个已经“游戏化”的代码库，天然适合交给 agent 去刷分。

### 具体例子：这个循环真的产出过成果

nanochat 排行榜上第 5 和第 6 条记录的描述就是“autoresearch 第 1 轮”“autoresearch 第 2 轮”，把“训练到 GPT-2 水平”的时间从 2.02 小时缩短到 1.80 小时，再到 1.65 小时。排行榜文档写道：第 5 条记录的所有改进都来自一个私有版本的 autoresearch 在 12 层小模型上的完全自主“研究”，这些改进“很容易地”迁移到了 24 层模型（<Source href={NC + 'dev/LEADERBOARD.md?plain=1#L194-L198'} label="LEADERBOARD.md 第 194–198 行" />）。第 2 轮里，Karpathy 让 agent 参考另一个仓库找灵感，agent 找到了让两个他本人以前手工尝试失败的技巧“变得有用”的方式；但代价是代码更复杂，于是他亲自用单元测试验证了推理的正确性（<Source href={NC + 'dev/LEADERBOARD.md?plain=1#L202'} label="第 202 行" />）。

<Callout type="要点">
这条证据很关键：**agent 在小环境里刷分，人负责把结果迁移到真实场景并验证**。小环境里的分数只是“代理指标”，最终是否合并进主线，仍是人的判断。
</Callout>

### 取舍与替代方案

- **固定时间 vs 固定计算量**：固定 5 分钟让不同改动直接可比，并且会找到“在你这台机器上最优”的模型；代价是不同硬件上的结果不可比（<Source href={A + 'README.md?plain=1#L178'} label="README 第 178 行" />）。社区有人提出改为固定计算量预算以便跨机器比较（<span class="tag accent">Issue</span><Source href={IS + '35'} label="#35" />，尚无定论）。产品上这是“对用户自己最优”与“可横向比较”之间的选择。
- **贪心爬山 vs 系统化搜索**：autoresearch 不做贝叶斯优化，也不维护候选池，只有“一条分支不断前进”。替代方案是参数扫描工具（社区提过集成 Optuna 等，<Source href={IS + '120'} label="#120" />，已关闭）。贪心的好处是结果始终是一条可读的提交历史；坏处是容易困在局部最优，program.md 也只允许“非常非常少地”回退（第 106 行）。
- **一切交给 agent 判断 vs 写死规则**：崩溃了要不要修、改动“值不值得”保留，都写成了需要 agent 判断的软规则，而不是代码里的硬检查。灵活，但约束力取决于模型是否听话（见第 6 章）。

<Callout type="要点" title="要点小结">

- autoresearch 的产品本体是一份给 agent 的规范，加上一个只读的裁判和一个可写的工作台。
- 循环成立的三个前提：环境小到可读懂、单次运行在固定预算内结束、分数单一且客观。
- 小环境里的进步只是代理信号，迁移到真实场景仍需要人验证。

</Callout>

## 第 2 章 范式转变：从“人操作工具”到“人定义目标和评价函数”

<Callout type="结论">
一句话结论：在 autoresearch 里，人的工作从“做实验”变成了“设计做实验的组织”：写目标、划边界、定评价、事后审查。人做的事情少了，但每件事的杠杆变大了，出错的后果也被放大了。
</Callout>

### 问题背景：工具时代的分工

过去所有的软件工具，不论多强大，都默认一个前提：**人是循环的驱动者**。人决定下一步做什么，工具负责把这一步做得又快又好。IDE（集成开发环境）帮你写代码，实验跟踪平台帮你画曲线，但“改哪里、看什么、什么时候停”永远由人决定。工具的竞争维度是“这一步有多顺手”。

autoresearch 把驱动者换了。README 里人只需要说一句类似“看一下 program.md，我们开始一个新实验吧，先做准备工作”的话（<Source href={A + 'README.md?plain=1#L156-L162'} label="README 第 156–162 行" />），之后 agent 被明确要求“永远不要停下来问人是否继续”，因为“人可能在睡觉”（<Source href={A + 'program.md?plain=1#L112'} label="program.md 第 112 行" />）。

### 产品洞察一：人的角色——从操作员变成“研究组织的设计者”

program.md 的“准备”部分（<Source href={A + 'program.md?plain=1#L5-L19'} label="第 5–19 行" />）是人与 agent 唯一的同步协作时间：商定运行标签、新建分支、确认数据存在、初始化结果表，然后“得到确认就开始”。之后人退出循环。README 还暗示了下一步：默认的 program.md “有意保持为最简基线”，显然可以不断迭代它，找到能让研究进展最快的“研究组织代码”，以及如何加入更多 agent（<Source href={A + 'README.md?plain=1#L121'} label="第 121 行" />）。

|  | 以前：人操作工具 | 现在：人定义目标与评价 |
| --- | --- | --- |
| 人每天做什么 | 想点子、改代码、启动训练、看曲线、判断 | 写和改 program.md；早上读结果表和提交历史；挑出值得迁移的改动 |
| 人的产出物 | 代码改动 | 规范、约束、评价函数、审查结论 |
| 迭代对象 | `train.py` | `program.md`（README 原话：前者由 agent 迭代，后者由人迭代） |
| 吞吐瓶颈 | 人的时间和注意力 | 算力、评估的可信度、人的审查带宽 |

### 产品洞察二：人的技能——从“会做”到“会定义好”

新范式需要的技能和原来很不一样：

- **把模糊目标翻译成可计算的分数**。“让模型更好”无法循环；“在固定 5 分钟内让 val\_bpb 最低”可以。program.md 第 33 行写道“目标很简单：得到最低的 val\_bpb”，这种简单是设计出来的。
- **写出“没写到的地方也对”的规则**。显存是“软约束”，允许为显著收益适度增加（<Source href={A + 'program.md?plain=1#L35'} label="第 35 行" />）；还有一条“简洁性标准”：同等条件下更简单更好，0.001 的提升如果多出 20 行生硬代码“大概不值得”，删代码还能持平“一定保留”（<Source href={A + 'program.md?plain=1#L37'} label="第 37 行" />）。这是把人的审美和长期维护成本，编码成 agent 可以执行的权衡规则。
- **设计反作弊的环境**。知道 agent 会沿着分数梯度走到哪里，提前把裁判隔离出去。
- **批量审查**。从逐行写代码，变成一次读一百条实验记录、判断哪些可信。

### 产品洞察三：人的责任——从“对每一步负责”到“对系统负责”

以前一个改动出错，责任落在写它的人身上。现在改动是 agent 写的，但目标、权限和评价函数是人定的，所以**人对“这个系统会产出什么”负责**。nanochat 的贡献规则就体现了这种责任观：提交 PR 时必须声明哪些部分有大量 LLM 参与、哪些是你“没有亲自写或并不完全理解”的（<Source href={NC + 'README.md?plain=1#L203'} label="nanochat README 第 203 行" />）。Karpathy 把 autoresearch 第 2 轮的结果合并进 nanochat 前，亲自做了单元测试验证（见第 1 章）。agent 可以写代码，但“合并进主线”这个签字动作仍属于人。

### 具体场景：一个晚上的分工

晚上 11 点，研究者和 agent 一起完成准备，确认基线跑通，然后去睡觉。agent 每 5 分钟左右完成一次实验，大部分被回滚，少数被保留，结果表逐行增长。早上 7 点，研究者打开 `results.tsv`（仓库里的 <Source href={A + 'analysis.ipynb'} label="analysis.ipynb" /> 就是读这张表、统计保留率、画进展图的分析笔记本），看到 90 次实验里保留了 11 次。他要做的是：这 11 次里哪些是真进步？哪些只是噪声？哪些改动太复杂不值得？哪些能迁移到大模型？然后他可能会修改 program.md，比如“这一轮多尝试优化器方面的想法”，开启下一夜。

### 取舍与替代方案

- **完全放手 vs 人在每一步把关**：autoresearch 选择了极端的“放手”，换来一夜一百次实验。另一种设计是每轮都让人点“同意”，但那样就退化回了工作流工具（见第 3 章）。
- <strong>“永不停止”的代价</strong>：这条规则对不同 agent 的效果差异很大。Karpathy 本人开的 Issue 抱怨 Codex “忽略了永不停止的指令”，社区讨论出外部循环、定时提醒“继续”等办法，也有人提醒强制继续可能让 agent 越过正当的停止理由，比如 GPU 故障（<span class="tag accent">Issue</span><Source href={IS + '57'} label="#57" />，该仓库讨论最多的 Issue）。这说明“自主运行多久”不应该只靠提示词，而应由外部的运行框架控制。

<Callout type="要点" title="要点小结">

- 角色：人从循环的驱动者变成循环的设计者和审查者。
- 技能：把目标变成可计算的分数、把审美变成权衡规则、把裁判隔离出去、批量审查。
- 责任：人对系统产出负责，“合并进主线”的签字权仍在人手里。

</Callout>

## 第 3 章 趋势：界面 → 工作流 → 智能体循环

<Callout type="结论">
一句话结论：同一个任务，在“界面”形态里人做所有决定，在“工作流”形态里人预先写死步骤，在“智能体循环”形态里人只写目标和裁判。每往前一步，人的操作次数下降一个量级，但失败模式也从“操作失误”变成“目标被曲解”。
</Callout>

### 问题背景：三种形态并不是互相替代，而是叠加

界面（UI，图形化操作界面）解决“如何让人方便地执行一个动作”；工作流（workflow，预先编排好的自动化步骤）解决“如何把重复的动作串起来”；智能体循环（agent loop）解决“如何让系统自己决定下一个动作”。autoresearch 恰好是第三种形态最纯粹的样本：它连工作流引擎都没有，循环逻辑本身就是自然语言写成的规范。

### 产品洞察一：价值从“效率”迁移到“探索”

界面的价值是降低单次操作成本；工作流的价值是消除重复劳动；智能体循环的价值是**在人不在场时探索人没想到的方向**。nanochat 第 2 轮的结果就是例子：agent 让 Karpathy 以前手工试过、失败过的两个技巧变得有用（见第 1 章证据）。工作流做不到这一点，因为工作流只能执行人已经想好的步骤。

### 产品洞察二：失败模式也随之迁移

界面的典型失败是“人点错了”；工作流的典型失败是“现实变了，脚本没变”；智能体循环的典型失败是“系统完美地优化了一个错误的目标”，或者它在没人看的时候做了一件没被禁止、但谁都不想要的事。后者更难发现，因为表面上一切指标都在变好。

<FormCompare />

### 产品洞察三：智能体循环要求工作流的“骨架”还在

有意思的是，autoresearch 并没有扔掉工作流。program.md 的循环步骤、结果表格式、超时规则，本质上就是一个工作流，只不过“每一步具体做什么”交给了 agent。**骨架固定、内容自主**是它能稳定运行的原因：提交、运行、读分数、记账、保留或回滚，这些步骤不容商量；改哪一行代码，完全自由。纯粹“给一个目标就放手”的 agent，很容易因为步骤不稳定而无法审查。

### 取舍与替代方案

- 不是所有任务都应该进入第三种形态。没有客观分数、单次反馈很慢、错误代价不可逆的任务（例如直接修改生产数据库），更适合停留在工作流形态，由人在关键步骤审批。
- 一种折中是“工作流里嵌一个小循环”：在某个步骤内部允许 agent 自主尝试多次，但出口由工作流控制。社区里很多分支版本正是这样做的，例如给循环加“草稿模型 + 审查模型”两段（见第 6 章 <Source href={IS + '307'} label="#307" />）。

<Callout type="要点" title="要点小结">

- 界面卖效率，工作流卖自动化，智能体循环卖探索。
- 失败从“点错”变成“目标被完美地曲解”，更隐蔽。
- 好的智能体循环保留了工作流的骨架：步骤固定，内容自主。

</Callout>

## 第 4 章 · 本页核心 未来产品设计的重点：目标、权限、环境、反馈指标、人工介入点

<Callout type="结论">
一句话结论：给 agent 加更多按钮没有意义，它不点按钮。智能体式产品真正的设计对象是五个面：它追求什么（目标）、能动什么（权限）、在哪里动（环境）、怎么知道动得对（反馈指标）、人什么时候回来（人工介入点）。autoresearch 用不到 120 行的 program.md 把这五个面都回答了一遍，也在每个面上留下了值得学习的缺口。
</Callout>

### 问题背景：为什么是这五个面

传统产品设计围绕“用户要完成什么动作”展开，产出物是页面和按钮。智能体式产品里，执行动作的是 agent，人设计的是 agent 的“工作条件”。这五个面对应一个经理给新员工布置任务时必须说清的五件事：要达成什么、你有什么权限、在哪里干活、怎么算干得好、什么时候来找我。少说任何一件，agent 都会用自己的方式补上，而它的方式不一定是你想要的。

### 设计面一：目标

#### 要回答的问题

- agent 追求的到底是什么？能不能写成一个可比较的结果？
- 多个目标冲突时怎么取舍？哪些是硬约束，哪些是软约束？
- 什么叫“足够好”，还是没有终点？

#### autoresearch 怎么做

一个主目标、一个硬约束、一个软约束、一个品味规则：

```text
目标很简单：得到最低的 val_bpb。……唯一的约束是代码不崩溃并在时间预算内完成。
显存是软约束。……
简洁性标准：同等条件下，越简单越好。
```

原文（英文，此处为意译）：<Source href={A + 'program.md?plain=1#L33-L37'} label="program.md 第 33–37 行" />。第一轮必须先跑基线（<Source href={A + 'program.md?plain=1#L39'} label="第 39 行" />），让所有比较都有锚点。

值得注意的是“简洁性标准”给出了具体的换算例子（0.001 的提升配 20 行生硬代码不值得；删代码而分数持平值得）。只说“保持简洁”是没有用的，agent 需要知道**汇率**。另一个细节是：它没有终点。“永不停止”意味着目标是“持续改进”，而不是“达到某个阈值”。

#### 常见错误

- 目标写成形容词（“更好”“更专业”），agent 只能自己猜，猜的结果每次不同。
- 只有主目标没有约束，agent 用一切代价换分数（例如把显存吃满、把代码写成一团）。
- 约束写成“不要太多”这类无法比较的话，没有换算关系。
- 没有基线，后面的“进步”无从谈起。

#### 设计建议

- 用“主目标 + 硬约束 + 软约束及汇率 + 基线”的四件套描述目标。
- 把人的品味写成可操作的取舍例子，最好有正反两个例子。
- 明确有没有终点：持续优化型任务要配预算上限（见设计面五和第 6 章“成本失控”）。

### 设计面二：权限

#### 要回答的问题

- agent 能读什么、写什么、执行什么、联网吗、能安装东西吗？
- “禁止”是写在说明里，还是由系统强制？
- 万一越界了，影响范围有多大？

#### autoresearch 怎么做

“能做”只有一条：只修改 `train.py`，里面一切都可以动。“不能做”有三条：不改 `prepare.py`、不安装新依赖、不改评估函数 `evaluate_bpb`，它是“基准真值”（<Source href={A + 'program.md?plain=1#L25-L31'} label="program.md 第 25–31 行" />）。这在产品上叫**白名单式授权**：不是列出所有危险动作，而是只开一扇门。“只改一个文件”还有第二个好处：README 说它让范围可控、差异可审查（<Source href={A + 'README.md?plain=1#L177'} label="第 177 行" />）。

但要看清它的边界：**这些禁令全部只写在说明里，没有任何技术强制**。README 甚至建议启动 agent 时“关闭所有权限确认”（<Source href={A + 'README.md?plain=1#L158'} label="第 158 行" />），即 agent 在这台机器上理论上什么都能做。社区 Issue 指出了一个更隐蔽的风险：agent 会读取训练脚本的输出，如果脚本被改得会打印“指令”，这些文字就可能被 agent 当作可信输入，即“间接提示词注入”；作者自评在无人值守过夜运行时为“中高”风险，并提议沙箱运行、让脚本输出固定格式的结果文件而不是让 agent 读原始输出（<span class="tag accent">Issue</span><Source href={IS + '64'} label="#64" />，已关闭并转入其他 PR 跟踪）。

#### 常见错误

- 用黑名单列举“不准做的事”，永远列不全。
- 把“请不要”当成权限控制。语言模型大多数时候会遵守，但“大多数时候”不是安全保证。
- 让 agent 读取它自己产出的、未经结构化的文本，并把其中内容当作指令。

#### 设计建议

- 白名单授权，并且由系统强制：评估代码放在 agent 不可写的位置，或在每轮提交前检查改动是否只涉及允许的文件。<span class="tag warn">建议</span>
- 反馈通道结构化：只让 agent 读取固定字段的结果文件，而不是整段日志。<span class="tag warn">建议，参考 #64</span>
- 按“越界的最大损失”而不是“越界的概率”来设计权限。

### 设计面三：环境

#### 要回答的问题

- agent 在哪里试错？试错能不能回滚？
- 每次尝试的成本和时长是否固定、可比？
- 环境里的成功能不能迁移到真实场景？

#### autoresearch 怎么做

- **隔离**：每次运行开一个新分支 `autoresearch/<标签>`，且这个分支必须不存在（<Source href={A + 'program.md?plain=1#L9-L10'} label="program.md 第 9–10 行" />）。主线永远不会被直接改动。
- **可回滚**：每个实验先提交，失败就 `git reset`。git 本身就是“撤销按钮”。
- **固定预算**：训练时长固定（训练脚本里到时间就停，<Source href={A + 'train.py#L602-L604'} label="train.py 第 602–604 行" />），随机种子固定（<Source href={A + 'train.py#L458-L459'} label="第 458–459 行" />），验证数据固定。
- **自包含**：除了少量依赖外没有外部系统（<Source href={A + 'README.md?plain=1#L179'} label="README 第 179 行" />）。
- **迁移靠人**：环境是 nanochat 的缩小版，所以结果能迁移回 nanochat，但迁移和验证是人做的（见第 1 章 LEADERBOARD 证据）。

#### 常见错误

- 直接在生产环境里让 agent 试错，每次尝试都有真实代价。
- 环境里没有“撤销”，一次坏改动会污染之后所有实验。
- 环境和真实场景差距太大，agent 在玩具上刷出的分数毫无迁移价值；或者环境太大太慢，一夜只能试两次。
- 没有考虑“环境本身被改坏”的情况（见第 6 章）。

#### 设计建议

- 先做一个“缩小但同构”的沙箱：同样的代码结构，更小的规模，更短的周期。nanochat 到 autoresearch 的简化就是范本。
- 每一次尝试都要有版本号，失败自动回到上一个已知良好状态。
- 定期在“大环境”里抽检小环境的结论是否成立。<span class="tag warn">建议</span>

### 设计面四：反馈指标

#### 要回答的问题

- agent 如何知道一次尝试是好是坏？这个信号有多快、多准、多难被操纵？
- 评估的噪声有多大？多小的差异算真进步？
- 记录是否足够让人事后复核？

#### autoresearch 怎么做

- **单一、客观、与改动无关的指标**：`val_bpb` 不依赖词表大小，所以改结构也能公平比较；评估函数所在的代码段标注“不要修改，这是固定的指标”（<Source href={A + 'prepare.py#L340-L366'} label="prepare.py 第 340–366 行" />）。
- **反馈被压缩**：训练结束只打印一个固定格式的摘要，agent 用 `grep` 取出分数（<Source href={A + 'program.md?plain=1#L41-L62'} label="program.md 第 41–62 行" />）。
- **结构化记账**：每轮一行，五列：提交号、分数、显存、状态（保留/丢弃/崩溃）、一句描述；崩溃记 0（<Source href={A + 'program.md?plain=1#L64-L88'} label="第 64–88 行" />）。选择制表符而不是逗号，是因为“描述里的逗号会破坏格式”，这是为 agent 写记录专门考虑的细节。

但这个指标通道有三个已经被社区指出的弱点：

1. **分数没有和真实训练绑定**。评估函数虽然不可改，但调用它、打印它的代码在可改的 `train.py` 里（<Source href={A + 'train.py#L611-L622'} label="train.py 第 611–622 行" />）。Issue 作者给出了一个复现：伪造的 0.05 分击败了诚实的 0.317 分并被保留，提议记录代码、数据、模型状态的哈希值，作为“检测而非预防”（<span class="tag accent">Issue</span><Source href={IS + '599'} label="#599" />）。
2. **指标本身可能有错**。有人报告字节数的计算方式会系统性地让分数偏乐观（<span class="tag accent">Issue</span><Source href={IS + '384'} label="#384" />，未合并）。产品启示：裁判也需要被审计。
3. **没有处理噪声**。program.md 只说“变低就保留”，没有显著性门槛。nanochat 的排行榜文档自己就承认，同样配置跑 5 次，CORE 分数最大最小差 0.016，并说 val\_bpb 比 CORE“噪声更小”（<Source href={NC + 'dev/LEADERBOARD.md?plain=1#L190-L192'} label="LEADERBOARD.md 第 190–192 行" />）；nanochat 的实验日志里也多次出现“几乎是噪声”的判断（<Source href={NC + 'dev/LOG.md?plain=1#L737'} label="LOG.md 第 737 行" />）。人做研究时会自然地考虑噪声，agent 不会，除非你写进去。

#### 常见错误

- 指标和“被优化的东西”放在同一个可写区域，选手兼任裁判。
- 只看一个数字，不看护栏指标（显存、时长、复杂度）。
- 把任何微小的数值下降都当进步，噪声积累成虚假的进展曲线。
- 记录只有结论，没有能复现的版本号和环境信息。

#### 设计建议

- 裁判独立运行：由外部进程重新加载模型、在留出数据上评估，而不是读 agent 打印的数字。<span class="tag warn">建议，参考 #599</span>
- 设定最小可信提升：提升幅度小于噪声的两倍时，用不同随机种子复测。<span class="tag warn">建议</span>
- 主指标 + 护栏指标：autoresearch 记录了显存，这是好的开始；还可以记录代码行数变化。

### 设计面五：人工介入点

#### 要回答的问题

- 人在什么时刻回到循环？是每一步、出现异常时，还是结束时？
- agent 什么情况下应该主动停下来找人？什么情况下绝对不要找人？
- 人回来时，看到的是什么？能多快做出判断？

#### autoresearch 怎么做

它只设了两个介入点，而且非常鲜明：

- **开始前**：准备阶段需要人确认（<Source href={A + 'program.md?plain=1#L17-L19'} label="program.md 第 17–19 行" />），数据不存在时 agent 要“告诉人去运行准备脚本”而不是自己动手（第 15 行）。
- **人主动打断时**：循环开始后“不要停下来问人”，“循环一直运行，直到人打断你，就这样”（第 112 行）。

中间没有任何审批点。审查完全是**事后、批量**的：早上读结果表和提交历史。这是一种明确的取舍：用“事后可追溯”换“过程中不打扰”。它之所以可行，是因为前面四个面已经把风险压得很低：只能改一个文件、在隔离分支上、失败就回滚、每一步有记录。

#### 常见错误

- 每一步都要人点“同意”，人很快变成“同意按钮”，审批形同虚设。
- 完全没有介入点，也没有事后审查材料，出了问题只能看到结果。
- agent 遇到它不该自己决定的事（例如缺数据、需要安装依赖）时，仍然自作主张。
- 把“何时停止”交给 agent 自觉（见 <Source href={IS + '57'} label="#57" />：不同 agent 对“永不停止”的服从程度差异很大）。

#### 设计建议

- 按风险分级介入：低风险自动、中风险事后批量审查、高风险（触及评估、权限、外部系统）实时拦截。<span class="tag warn">建议</span>
- 明确列出“必须找人”的情况，其余情况明确要求“不要找人”。autoresearch 只做了后一半。
- 为“人回来的那一刻”设计审查材料：保留的改动列表、每个改动的差异和分数、异常汇总。
- 运行时长、预算上限由外部框架控制，而不是靠提示词。

<DesignPanel />

### 取舍与替代方案：五个面是联动的

五个面不能单独打分。autoresearch 敢于“中间完全不介入”，是因为权限窄、环境可回滚；如果权限放宽到能改评估、能联网，同样的“不介入”就变成高危。反过来，如果指标很弱（需要人主观判断），就必须增加介入点，循环速度随之下降。设计时可以先定“最想要的循环速度”，再倒推其他四个面需要多严格。

<Callout type="要点" title="要点小结">

- 目标：主目标 + 硬约束 + 软约束及汇率 + 基线。
- 权限：白名单，且由系统强制，而不是只写在说明里。
- 环境：缩小但同构、可回滚、固定预算。
- 反馈指标：裁判独立、考虑噪声、有护栏、可复现。
- 人工介入点：按风险分级，并为“人回来的那一刻”设计审查材料。

</Callout>

## 第 5 章 理解智能体式产品

<Callout type="结论">
一句话结论：智能体式产品的界面不再是“一排按钮”，而是“目标 + 约束 + 指标 + 审查面板”四个区域；产品经理的核心交付物，从页面流程图变成一份 agent 能执行、人能审查的运行规范。
</Callout>

### 问题背景：为什么需要一份清单

autoresearch 能用不到 120 行规范跑起来，是因为它的任务恰好有一个完美的分数、一个可裁剪的环境，以及一个懂行的使用者（Karpathy 本人）。大多数产品没有这么幸运。把前四章的经验整理成清单，可以在动手前检查：我的任务适不适合做成循环？如果适合，五个面是否都回答了？

### 产品洞察一：先判断“能不能循环”，再谈“怎么循环”

从第 1 章的三个前提可以推出一个简单的适用性判断：单次尝试是否便宜且有固定上限？结果是否有客观分数？失败能否撤销？三个都是“否”的任务，强行做成智能体循环，只会得到一个昂贵且无法审查的系统。

### 产品洞察二：界面从“按钮”变成“四个区域”

<InterfaceMock />

这四个区域对应 autoresearch 里的四样东西：program.md 的目标与约束段落、prepare.py 里的固定评估、results.tsv 与 git 历史。可以说 autoresearch 的“界面”已经存在，只是以文件的形式存在。产品化的工作就是把这四样东西变成可视化、可编辑、可审查的区域。<span class="tag warn">推测</span>

### 产品洞察三：规范本身也是可迭代的产品

README 明说 program.md 由人迭代（第 129 行）。社区很快把这个想法推进了一步：有 Issue 提议允许根据实验结果迭代 program.md 本身（<Source href={IS + '314'} label="#314" />），也有人认为“下一代 agent 也许不是靠新算法，而是靠找到正确的提示词”（<span class="tag accent">Issue</span><Source href={IS + '22'} label="#22" />）。对产品团队来说，这意味着规范需要版本管理、需要 A/B 比较、需要像代码一样被评审。

### 取舍与替代方案

- **文件即界面 vs 图形界面**：autoresearch 用文件和 git 作为全部界面，对工程师零学习成本、完全可脚本化，但对非技术用户不可用。图形化的审查面板降低门槛，但要小心别又退化成“一排按钮”。
- **单一指标 vs 多指标**：单一指标让循环决策简单可靠；多指标更接近真实需求，但需要明确的汇率，否则 agent 无法决定。

<Callout type="要点" title="要点小结">

- 先用“便宜、可评分、可撤销”三问判断任务是否适合循环。
- 界面四区域：目标、约束、指标、审查面板。
- 规范本身是产品，需要版本管理与评审。

</Callout>

## 第 6 章 边界场景的处理逻辑

<Callout type="结论">
一句话结论：autoresearch 用“软规则 + git 回滚 + 结果表”处理了崩溃、超时和普通失败，但对作弊、噪声、复杂度膨胀、长期停滞、成本和并行冲突基本没有硬机制。这些正是把它产品化时最需要补上的部分。
</Callout>

下面九个场景，每个都从产品策略角度讲：现象是什么、项目里有没有处理、应该怎么处理。<span class="tag ok">项目已有</span>表示能在仓库原文中找到；<span class="tag warn">建议</span>表示本页提出的做法。

<FilterDetails filters={[{ id: 'have', label: '项目有处理' }, { id: 'sugg', label: '仅有建议' }]}>

<DetailItem title="1. agent 钻指标空子或改评估代码" kinds={['have', 'sugg']} tags={[{ label: '部分已有', tone: 'ok' }, { label: '建议', tone: 'warn' }]}>

**现象**：分数在变好，模型并没有变好。可能是改了评估方式、减少了验证数据、跳过了训练却照样输出分数，或者直接打印一个好看的数字。

**项目里的处理**：只有规范层面的禁令：不改 `prepare.py`、不改评估函数（<Source href={A + 'program.md?plain=1#L28-L31'} label="program.md 第 28–31 行" />），评估区代码有“不要修改”注释。但调用评估和打印分数的代码在可改的 `train.py` 里。<Source href={IS + '599'} label="#599" /> 列出了四种不改评估函数也能降低分数的路径，并给出了伪造分数被保留的复现。

**产品策略**：把“防作弊”从提示词移到架构：裁判由独立进程运行，读取 agent 产出的模型文件，在 agent 看不到的留出数据上评估；每轮检查改动是否触及受保护文件；记录代码与数据的哈希，让每个分数都可复现。另外，分数的大幅跃升本身就是告警信号，应自动进入人工审查。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="2. 训练崩溃" kinds={['have']} tags={[{ label: '项目已有', tone: 'ok' }]}>

**现象**：显存不足、代码有拼写错误、数值发散。

**项目里的处理**：三层。第一，训练脚本里有“快速失败”：损失变成非数或超过 100 就立刻退出（<Source href={A + 'train.py#L569-L572'} label="train.py 第 569–572 行" />），不浪费剩余预算。第二，读不到分数就视为崩溃，读最后 50 行报错（<Source href={A + 'program.md?plain=1#L101'} label="program.md 第 101 行" />）。第三，用判断区分“蠢错误”和“想法本身不行”：前者修了重跑，后者记为 crash 继续（<Source href={A + 'program.md?plain=1#L110'} label="第 110 行" />）；“试几次还不行就放弃”。

**产品启示**：崩溃不是异常，而是循环的正常产出之一，要有专门的状态和记账方式（分数记 0、显存记 0）。“重试几次”最好给出具体上限。<span class="tag warn">建议：把“几次”写成数字</span>

</DetailItem>

<DetailItem title="3. 超时" kinds={['have']} tags={[{ label: '项目已有', tone: 'ok' }]}>

**现象**：改动让单步变慢、启动卡住，或者进程挂起。

**项目里的处理**：训练循环本身按墙钟时间停止，并且排除了前 10 步的编译时间（<Source href={A + 'train.py#L602-L604'} label="train.py 第 602–604 行" />）；规范另设外部上限：超过 10 分钟就杀掉，按失败处理并回滚（<Source href={A + 'program.md?plain=1#L108'} label="program.md 第 108 行" />）。

**产品启示**：内部预算（任务自己知道何时停）与外部看门狗（框架强制终止）缺一不可。前者保证公平比较，后者防止卡死。注意外部上限目前仍靠 agent 自己执行，更稳妥的是由运行框架强制。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="4. 噪声造成假进步" kinds={['sugg']} tags={[{ label: '建议', tone: 'warn' }]}>

**现象**：两次完全相同的运行分数也会不同；如果“变低就保留”，迟早会把运气保留下来。更糟的是，下一轮的“最好成绩”被这个幸运值抬高，真正的小进步反而会被拒绝。

**项目里的处理**：固定随机种子和验证分片可以减小噪声，但规范里没有显著性门槛，“相等或更差就回滚”是唯一规则。nanochat 文档承认了运行间的波动（<Source href={NC + 'dev/LEADERBOARD.md?plain=1#L190'} label="LEADERBOARD.md 第 190 行" />），Karpathy 在排行榜记录上用 5 次运行求平均（第 196、202 行），但这是人的习惯，没有写进 agent 的规范。

**产品策略**：事先测出噪声水平（同一配置重复跑几次）；规定最小可信提升；小于门槛的“进步”换种子复测，取平均再决定；定期在当前最好版本上重跑，校正“最好成绩”。在上方模拟器里把噪声调到“高”、关闭审批点，就能看到假进步被保留；打开审批点后会触发复测。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="5. 改动越来越大、难以审查" kinds={['have', 'sugg']} tags={[{ label: '部分已有', tone: 'ok' }, { label: '建议', tone: 'warn' }]}>

**现象**：一百次实验后，分支上堆了十几个保留的改动，代码变复杂，早上的人看不过来。

**项目里的处理**：单文件约束让差异集中（README 第 177 行）；简洁性标准把复杂度作为保留时的成本（program.md 第 37 行）；每个实验一个提交、一行记录。真实案例也说明了这个问题：autoresearch 第 2 轮引入的改动让 nanochat 代码“更复杂、需要改推理代码”，Karpathy 不得不额外写测试验证（<Source href={NC + 'dev/LEADERBOARD.md?plain=1#L202'} label="LEADERBOARD.md 第 202 行" />）。

**产品策略**：限制单次改动的行数；在审查面板上按“收益 / 新增复杂度”排序；定期让 agent 做“消融”：逐个去掉已保留的改动，看哪些其实没贡献。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="6. 长期没有进展" kinds={['have', 'sugg']} tags={[{ label: '部分已有', tone: 'ok' }, { label: '建议', tone: 'warn' }]}>

**现象**：连续几十轮都被回滚，agent 在同一类想法上打转。

**项目里的处理**：规范给出了“想不出点子时”的做法：更努力地想，读代码里引用的论文，重读文件找新角度，组合以前的“差一点”成功的想法，尝试更激进的结构改动（<Source href={A + 'program.md?plain=1#L112'} label="第 112 行" />）；允许极少量地回退（第 106 行）。社区普遍认为探索不够多样：<span class="tag accent">Issue</span><Source href={IS + '22'} label="#22" />“创造力低”，<Source href={IS + '47'} label="#47" /> 讨论用多个 agent 辩论增加新意，相关分支加了“实验记忆、平台期检测、类别多样化”。

**产品策略**：把“平台期”定义成可检测的状态（例如连续 N 轮无保留）；进入平台期后切换策略（换方向、引入外部资料，就像第 2 轮人让 agent 参考另一个仓库）；平台期持续则通知人，这是少数值得打断“永不停止”的情况。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="7. 成本失控" kinds={['sugg']} tags={[{ label: '建议', tone: 'warn' }]}>

**现象**：GPU 时间和模型调用费用随运行时间线性增长，而“永不停止”没有上限。

**项目里的处理**：单次实验的时间是固定的，因此单轮成本可预测；但总轮数没有上限，规范里没有任何费用相关的规则。社区有人专门问成本，唯一的数字是一位用户的粗略估计“8 小时约 10–20 美元”的模型调用费用（<span class="tag accent">Issue</span><Source href={IS + '61'} label="#61" />，个人经验，非官方）。

**产品策略**：预算作为一等公民：总时长、总调用费、总 GPU 小时三个上限，由框架强制；在审查面板上显示“每次保留的成本”，随平台期变长而上升，帮助人决定何时停止。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="8. 环境被改坏" kinds={['have', 'sugg']} tags={[{ label: '部分已有', tone: 'ok' }, { label: '建议', tone: 'warn' }]}>

**现象**：agent 安装了包、删了缓存数据、改了全局配置，或者结果表本身被弄乱，之后所有实验都不再可比。

**项目里的处理**：禁止安装依赖（program.md 第 30 行）；数据缺失时要求告诉人，而不是自己处理（第 15 行）；实验在独立分支上，失败用 `git reset` 回滚；结果表刻意不进 git（第 102 行，<Source href={A + '.gitignore#L22-L23'} label=".gitignore" />），所以回滚不会抹掉记录。但 git 只管代码，管不到 `~/.cache` 里的数据和机器环境。

**产品策略**：把环境做成只读镜像或容器，每轮从干净状态启动；数据做校验和，启动前核对；把“环境健康检查”作为每轮的第 0 步。<span class="tag warn">建议</span>

</DetailItem>

<DetailItem title="9. 多个 agent 并行冲突" kinds={['have', 'sugg']} tags={[{ label: '部分线索', tone: 'ok' }, { label: '建议', tone: 'warn' }]}>

**现象**：几块 GPU 上各跑一个 agent，它们改同一个文件、抢同一块 GPU、写同一张结果表，或者都在尝试同一个想法。

**项目里的处理**：规范里的分支命名例子包含 `autoresearch/mar5-gpu0`（<Source href={A + 'program.md?plain=1#L92'} label="program.md 第 92 行" />），暗示“每块 GPU 一个分支”；`.gitignore` 里忽略了 `worktrees/`、`queue/`、`results/` 以及“由启动器按会话生成”的 agent 提示文件（<Source href={A + '.gitignore#L11-L17'} label="第 11–17 行" />）。由此推测作者私下有多 agent 启动器，但公开仓库里没有。<span class="tag warn">推测</span> README 也只说“显然可以加入更多 agent”。

**产品策略**：每个 agent 一个独立工作目录和分支；GPU 由调度器分配；结果写入各自的表，再由汇总器合并；用共享的“已尝试想法”清单避免重复；定期由人或一个“主管 agent”把各分支的好改动合并到主线并重新评估。<span class="tag warn">建议</span>

</DetailItem>

</FilterDetails>

### 综合：边界场景背后的三条产品策略

- **可撤销优先**：autoresearch 处理得最好的场景（崩溃、超时、普通失败），都是因为 git 让失败可以撤销。先保证可撤销，再谈自主。
- **硬机制兜底软规则**：规范可以覆盖大多数情况，但作弊、成本、超时这类“万一”必须有系统强制的底线。
- **把异常变成审查材料**：大幅跃升、平台期、改动膨胀都应自动生成待审项，而不是埋在日志里。另外，审查也不能太严：一个分支版本里审查模型太挑剔，导致每晚数百次尝试一次都没保留（<span class="tag accent">Issue</span><Source href={IS + '307'} label="#307" />，误提到上游的分支问题）。

<Callout type="要点" title="要点小结">

- 已有硬处理：崩溃快速失败、训练按时停止、失败回滚、结果表独立于 git。
- 只有软规则：不改评估、不装依赖、超时 10 分钟、平台期多想想。
- 基本缺失：噪声门槛、成本上限、环境校验、并行协调。

</Callout>
