OpenAI Agents SDK：agent 应该怎么设计

这是 OpenAI 官方的 agent 开发框架（以 Python 版为主，必要时对照 JS/TS 版），由早期实验项目 Swarm 升级而来。本页不讲怎么写代码，而是看它替“做 agent 产品的人”做了哪些决定：一个 agent 由哪几块组成、一次运行按什么规则推进、什么时候必须停下来问人——以及更重要的一点：什么时候根本不该做成 agent。

分析版本：openai-agents-python 841dfdd，openai-agents-js be4f1f9；补充案例 OpenAI Codex 86e17e9。所有源码链接都指向这些提交的永久地址。标注“推测/建议”的内容为本页作者的判断，不来自仓库原文。

第 1 章 · 核心概念

八个原语，各管一件事

一句话结论Agents SDK 把一个 agent 产品拆成“一份岗位说明书（Agent）+ 一个按规则跑循环的执行器（Runner）”，其余能力——工具、交接、约束、追踪、会话记忆、结构化输出——都挂在这两者上。原语少，是它最核心的产品决定。

问题背景：每个团队都在重复写同一个循环

假如你直接调用模型接口做一个客服助手，要自己写这些事：把用户的话发给模型；模型说“我要查订单”，你得解析出它想调用的函数、执行、把结果塞回去再问一次；它说“这事该退款组处理”，你得换一套提示词接着聊；中途还要拦截恶意输入、检查回复有没有乱承诺、把每一步记下来方便排查。

这些代码几乎每个团队都在重复写，而且最容易出错的恰恰是边界：工具报错了怎么办？模型反复调用工具停不下来怎么办？两个工具同时被调用怎么办？用户中途点了“停止”怎么办？SDK 的出发点，就是把这套“循环 + 规则”做成标准件。它的文档写了两条设计原则：

官方的两条设计原则① 功能足够多，值得用；原语足够少，学得快。② 开箱即用，但每一步都能定制。另外它强调“以 Python 为先”：编排和串联 agent 用语言本身的能力（函数、循环、并发），而不是让你学一套新的流程描述语言。 docs/index.md

产品洞察一：Agent 不是“一个智能体”，而是“一份岗位说明书”

Agent（智能体配置）= 模型 + 指令（instructions，告诉它是谁、怎么做事）+ 工具 + 可以交接的同事 + 约束 + 期望的输出格式。它本身不会运行，只是一份静态配置。最贴切的类比是招聘时写的岗位说明书：你负责什么、能用哪些系统、遇到什么情况转给谁、交付物长什么样。

为什么要把“角色”和“运行”分开？因为同一份岗位说明可以在不同场合复用：测试时换便宜模型、上线时开追踪、给某个大客户加一条额外约束，都不用改 Agent 本身，只改这次运行的配置（RunConfig）。多 agent 时，每个岗位也能单独迭代、单独评估。 agent.py

与之配套的还有运行上下文（context）：你自己的对象（当前用户 ID、数据库连接、权限）可以传给工具和约束使用，但不会发给模型。这条边界很重要——“谁有权限退款”应该由代码判断，而不是写进提示词让模型自觉遵守。 docs/context.md

产品洞察二：真正“动”起来的是 Runner 的循环

Runner（运行器）负责 agent loop（智能体循环）：调用当前 agent 的模型 → 看模型输出——是最终答案就结束；要交接就换一个 agent 再来；要调用工具就执行、把结果追加进对话再来；超过 max_turns（最大轮数，默认 10）就报错。 docs/running_agents.md run_config.py#L45

要特别注意一个对应关系：一次 Runner.run 对应用户眼中的“一个回合”，内部可能调用好几次模型、经过好几个 agent。用户问一句，系统可能“想了四轮”才回答。这直接影响延迟和成本预算。

为什么循环要集中在 Runner？因为“循环的规则”就是“产品的行为规则”：什么时候算完成、什么时候必须停、什么时候换人。集中在一处，所有 agent 共享同一套语义，团队才能预测和排查 agent 的行为（第 3 章细讲）。

产品洞察三：工具、交接、约束、追踪——四个挂件

Tools（工具）：模型的手脚

模型只会生成文字，工具让它能“查”和“做”。SDK 提供五类：函数工具（把一个 Python 函数变成工具，参数说明从函数签名和注释自动生成）、OpenAI 托管工具（网页搜索、文件检索、代码解释器、托管 MCP、图像生成）、本地运行时工具（Shell、改文件、操作电脑）、把 agent 当工具、实验性的 Codex 工具。 docs/tools.md

产品要点：工具描述就是写给模型的使用手册；工具多了，模型选错的概率会上升推测。SDK 为此提供了“工具搜索 / 延迟加载”，让大量工具按需出现。

Handoffs（交接）：把对话转给更合适的同事

在模型看来，交接就是一个名叫 transfer_to_退款_agent 的工具。模型一调用它，Runner 就把“当前 agent”切换过去，新 agent 默认看到完整历史，并接着直接和用户说话。 handoffs/__init__.py

为什么需要：当一个 agent 的指令写到几千字、塞了几十个工具时，不同业务的规则会互相干扰。拆成专家后，每份指令都短而专注。

Guardrails（约束）：在主流程旁边站岗

三种：输入约束（只在第一个 agent 上运行）、输出约束（只在产出最终答案的 agent 上运行）、工具约束（每次调用受保护的函数工具前后运行）。一旦触发“绊线”（tripwire），立刻抛出异常、中止运行。默认与模型并行以免拖慢响应，也可以设为阻塞（先检查再开工）。 docs/guardrails.md

文档举的例子很“产品”：用一个便宜快速的模型判断用户是不是在让贵模型帮忙写数学作业，是就直接拒绝，省时间也省钱。

Tracing（追踪）：每一步都留下可回放的记录

默认开启。一次运行是一条 trace（轨迹），其中每个 agent、每次模型生成、每次工具调用、每次交接、每次约束检查都是一个 span（片段，有起止时间和父子关系）。 docs/tracing.md

为什么需要：agent 的行为是概率性的，读代码推断不出它这次做了什么。追踪是唯一的“黑匣子”，也是后续评估、微调的数据来源。

产品洞察四：会话记忆与结构化输出——让 agent 接得上人和程序

会话记忆（Sessions）：让第二句话记得第一句

Runner 每次只处理一个回合。要跨回合记住上下文，有四种做法：自己用 result.to_input_list() 拼接；交给 Session（会话存储：SQLite、Redis、SQLAlchemy、加密会话等）自动读写；或使用 OpenAI 服务器端的 conversation_id / previous_response_id。文档特别提醒：一个对话只选一种，混用会让上下文重复。 memory/session.py

结构化输出（output_type）：让结果能被程序接住

给 Agent 设定 output_type（例如一个 Pydantic 数据模型），最终输出必须通过校验才算“完成”；校验不过就报 ModelBehaviorError，或交给 invalid_final_output 错误处理器给出兜底结果。 agent.py#L383

为什么需要：agent 的结果经常要交给下游程序（工单系统、前端卡片），自由文本无法可靠解析。它还直接改变了“这一轮结束了没有”的判定（见第 3 章）。

issue #887 · 短期与长期记忆2025 年 6 月有用户问 SDK 是否内置短期/长期记忆。当时项目成员回复：“我不认为记忆会成为这个 SDK 的一等组件”，并指出当时连对话持久化都没有，issue 以“不计划”关闭。而在今天的版本里，Sessions 已经是 README 列出的核心概念之一——短期对话历史最终被认定为框架该管的事；长期记忆依然留给应用自己设计（后续评论还提醒：长期记忆会让提示词注入跨会话留存）。 #887

具体例子：官方的航空客服示例

仓库里的 examples/customer_service 用三个 agent 组成一个客服：分诊 agent 只负责转接，FAQ agent 用查询工具回答常见问题，选座 agent 负责改座位。两个专家都挂了一个 transfer_to_triage_agent，遇到不属于自己的问题就转回分诊。应用层每个回合结束后把 result.last_agent 记下来，下一回合直接从它开始——也就是“谁接手了，就继续由谁回答”。 customer_service/main.py

取舍与替代方案

它选择了：少量原语 + 流程控制交给模型或普通 Python 代码。它放弃了：像“图编排”类框架那样，事先用节点和边把流程画清楚的能力（SDK 只有一个可选的可视化扩展，用来画 agent 之间的关系图，而不是执行图）。 docs/visualization.md

代价是：如果你的流程本身很确定、需要严格控制（例如审批流必须经过 A→B→C），你得自己用代码编排几个 agent；好处是上手快，简单场景几行就能跑，复杂场景也不用学一套新语言。对做产品的人来说，这意味着流程的确定性需要你主动设计，框架不会替你强制。

要点小结
  • Agent 是静态的岗位说明书，Runner 才是让它动起来的循环；一次运行 = 用户的一个回合，内部可能有多轮模型调用。
  • 工具负责查和做，交接负责换人，约束负责拦，追踪负责记；会话记忆接住“人”，结构化输出接住“程序”。
  • 敏感的业务判断（权限、金额）放在运行上下文和代码里，不要放进提示词。
第 2 章 · 覆盖的能力

多 agent、沙箱、语音、MCP：各自解决什么场景

一句话结论四块能力分别回答四个问题：多 agent 编排回答“怎么分工”，沙箱回答“在真实文件和命令里干活”，实时/语音回答“用嘴说话时如何低延迟”，MCP 回答“怎么接入别人已经做好的工具”。每一块都有明确的“不需要”场景，默认不该全都用上。

问题背景：功能越多，越要问“什么时候不用”

一个 SDK 可以无限加功能，但看它把哪些东西做成一等公民，能看出 OpenAI 认为 agent 产品的主战场在哪。README 的核心概念清单里，除了基础原语，还专门列了沙箱 agent、实时 agent、语音 agent、人工介入、会话。下面逐个看它们解决什么场景、什么时候需要、什么时候不需要。 README.md

2.1 多 agent 编排：交接 与 agent-as-tool 两种模式

文档把多 agent 编排分成两大类：让模型来决定（交接、agent-as-tool）和用代码来决定（结构化输出分类后由代码选下一个 agent、链式串联、“生成—评审”循环、asyncio.gather 并行）。并直言代码编排“在速度、成本和效果上更确定、更可预测”。 docs/multi_agent.md

在“让模型决定”的方式里，两种模式的根本区别是谁持有对话：

维度交接（Handoff）agent-as-tool（把 agent 当工具）
谁持有对话专家接管，成为“当前 agent”经理始终持有，专家只是被调用一次
专家看到什么默认完整历史（可用过滤器裁剪）只看到经理为它生成的那段输入
谁写最终回复专家直接回复用户经理整合结果后回复
约束在哪生效输入约束在第一个 agent，输出约束在最后一个 agent经理那一层的约束统一生效
下一回合通常从 last_agent（专家）继续仍是经理
适合路由本身就是流程的一部分：客服分流、语言分流有边界的子任务、需要综合多个专家：多语言翻译、报告各章节

源码里 as_tool 的说明把区别写得很直白：“交接时新 agent 接收对话历史，而作为工具时新 agent 接收生成的输入；交接时新 agent 接管对话，而作为工具时对话由原 agent 继续。” agent.py#L630 两种也可以混用：分诊交接给专家，专家再把更小的子 agent 当工具调用。

issue #847 · “交接后永远拿不回控制权”有用户请求增加 back_handoff：专家办完后自动把控制权还给编排者。他的原话是“一旦 agent 把控制权交给另一个 agent，就再也拿不回来了”。维护者曾表示在考虑，最终以“不修复”关闭。官方示例的做法是让专家也挂一个转回分诊的交接。产品启示：交接是“转接电话”，不是“函数调用”；如果你要的是“办完回来汇报”，就该选 agent-as-tool。 #847
issue #864 · agent-as-tool 隐藏了子 agent 的内部过程用户反馈：把 agent 当工具后，父运行只能拿到子 agent 的最终字符串，看不到它内部调用了哪些工具，导致“并行跑多个子 agent 并实时显示进度”做不出来。后来 SDK 为 agent-as-tool 加了 on_stream 回调，维护者也说明这与原提案设计不同。产品启示：agent-as-tool 换来的是边界清晰，代价是过程黑盒化，用户等待体验需要额外设计。 #864

什么时候不需要多 agent：一个 agent 的指令和工具还能写清楚、测得过来时，就不要拆。拆分会带来转错人、多一次模型调用的延迟、交接时上下文丢失或泄露等新问题建议。文档自己的建议也是“让专精的 agent 擅长一件事”，而不是一开始就设计一张大网。

2.2 沙箱与代码执行：仓库里真实存在，而且是一等能力

以当前仓库为准，SDK 有一整套 Sandbox Agents（沙箱 agent）（src/agents/sandbox/），JS 版也有对应实现（packages/agents-core/src/sandbox）。它要解决的问题是：很多有价值的任务需要在真实文件系统里干活——搜大量文档、改代码、跑测试、生成文件，并且能隔天接着干。 sandbox_agent.py docs/sandbox/guide.md

  • SandboxAgent 仍然是 Agent：指令、工具、交接、约束、追踪都照旧，只是多了 Manifest（新工作区的初始内容：仓库、本地目录、云存储挂载）、能力包（文件系统工具、Shell、技能、记忆、历史压缩）和 SandboxRunConfig（这次用哪个沙箱后端）。
  • 沙箱后端可替换：本机（UnixLocal）、Docker、托管提供方（仓库扩展目录里有 E2B、Modal、Daytona、Cloudflare、Vercel、Blaxel）。agent 定义不变，换的是运行配置。
  • 隔离强度如实说明：文档警告，本机后端在 Linux 上“不加任何系统级隔离”，在 macOS 上只限制文件、不隔离网络；不可信的命令（包括受不可信输入影响的命令）应该用 Docker 或托管沙箱。 docs/sandbox_agents.md
  • 责任分层：“外层运行时仍然掌管审批、追踪、交接和恢复所需的状态；沙箱只管命令和文件变化。”这是一条很清晰的产品边界。

此外还有更轻量的选择：托管的代码解释器（CodeInterpreterTool）、托管容器 Shell、本地 ShellTool / ApplyPatchTool（注意它们默认不需要审批，要自己打开），以及实验性的 codex_tool（把 Codex 命令行包成一个工具，带沙箱模式和审批策略参数）。 docs/tools.md

什么时候需要 / 不需要需要：任务以工作区为中心（修 bug 并跑测试、处理一批文件生成表格、每个评审子 agent 各有独立工作区、分多次续作）。不需要：不访问文件、也不需要可变文件系统 → 普通 Agent；只是偶尔跑一条命令 → 托管 Shell 即可。文档原话：“如果工作区边界本身就是功能的一部分，才用沙箱 agent。”
真实产品对照：Codex 如何把“沙箱”做成用户设置OpenAI 的编码 agent 产品 Codex 把执行范围做成了三档：read-only（只读，默认）、workspace-write（只能写当前工作目录，出网默认关闭）、danger-full-access（完全访问，名字里就带着“危险”）。 config_types.rs protocol.rs 这正是 SDK 文档所说“隔离由后端决定”的产品化形态：默认最保守，放权需要用户显式选择，并且用命名提醒风险。

2.3 实时与语音对话

SDK 提供两条路，取舍完全不同：

语音流水线（VoicePipeline）

语音转文字 → 你的普通 agent 工作流 → 文字转语音。好处是能复用全部文本 agent 能力（结构化输出、所有工具、交接）；代价是三段串联，延迟更高，也不能自然地被打断推测。 docs/voice/pipeline.md

实时 agent（RealtimeAgent）

与实时接口保持长连接，增量处理音频、流式输出语音、可以被用户打断。它刻意比普通 Agent 更窄：模型在会话级别配置、不支持结构化输出、开口说话后不能再换声音；但指令、函数工具、交接、钩子和输出约束都保留。 realtime/agent.py docs/realtime/guide.md

平台边界也值得注意：Python 版只做服务器端 WebSocket 和 SIP（电话线路），不提供浏览器端 WebRTC；浏览器里直接语音对话的能力在 JS 版里（openaiRealtimeWebRtc.ts）。这是一个很合理的分工：Python 适合服务器编排和电话接入，JS 适合前端。 openaiRealtimeWebRtc.ts

什么时候需要 / 不需要需要实时 agent：电话客服、车载/硬件语音助手、需要被打断和即时反馈的对话。用语音流水线就够：语音只是外壳、背后是严格的表单流程或需要结构化输出。完全不需要：文本就能完成的任务——语音会显著提高测试和评估难度。

2.4 MCP：接入别人已经做好的工具

MCP（模型上下文协议）是让应用以标准方式向模型提供工具和上下文的开放协议。SDK 支持四种接入：托管 MCP（由 OpenAI 的 Responses 接口代为调用公网服务器）、Streamable HTTP、SSE、本地 stdio 进程；多个服务器用 MCPServerManager 统一管理。 docs/mcp.md

  • 信任先于连接：文档醒目警告“连接前先信任 MCP 服务器”——使用最小权限凭证、令牌放在请求头而非 URL 里、敏感操作要求审批。
  • 延迟与稳定：每次运行都会向每个服务器拉取工具列表；工具定义稳定时可开 cache_tools_list。连不上的服务器默认被剔除，只把连上的暴露给 agent（第 6 章）。
  • 治理：可静态或动态过滤暴露的工具；可以给本地 MCP 服务器统一挂工具约束和审批策略；多个服务器工具重名时可开启“工具名带服务器前缀”。
issue #23 · Add MCP supportSDK 发布当天（2025 年 3 月）就有人请求 MCP 支持，两周内落地。讨论中社区反对把另一个第三方 agent 框架整体并入，主张直接基于官方 MCP Python SDK——现在的实现正是依赖官方 mcp 包（兼容 v1 与 v2）。 #23
什么时候需要 / 不需要需要：工具由别的团队或厂商维护、要在多个 agent 产品间复用、要接入现成生态（文件系统、代码托管、数据库连接器）。不需要：只是你自己的两三个内部函数——直接写函数工具更简单、更好测，少一个进程或一次网络往返建议。

取舍与替代方案

这四块能力都遵循同一个思路：不新建平行体系，而是在 Agent / Runner 上扩展。沙箱 agent 是 Agent 的子类，实时 agent 保留交接和约束，MCP 工具和本地函数工具走同一条工具管道（因此能共享审批和约束）。代价是有些能力“打了折”（实时 agent 不支持结构化输出、托管工具不走工具约束管道），需要产品方清楚每条边界。

要点小结
  • 交接 = 转接电话，专家接管；agent-as-tool = 请同事帮忙，经理负责到底。需要“办完回来汇报”就别用交接。
  • 沙箱 agent 是真实的一等能力，但隔离强度取决于后端：本机后端几乎没有隔离。
  • 实时 agent 低延迟但更窄；语音流水线能力全但更慢。MCP 适合复用外部工具，自家小函数直接写工具即可。
第 3 章 · 重点

为什么是“模型 + 指令 + 工具 + 交接 + 约束 + 观测”这套系统

一句话结论这六块不是功能清单，而是一条责任链：模型负责“想”，指令负责“定角色”，工具负责“做”，交接负责“换人”，约束负责“拦”，观测负责“记”。Runner 用一套有固定优先级的规则把它们串成循环——理解这套规则，才能预测 agent 的行为，也才知道该在哪一块上加固。

问题背景：提示词解决不了结构问题

新手做 agent 最常见的失败，是把一切寄托在“更好的提示词”上。但提示词只能影响模型“想”什么，影响不了这些事：工具失败后系统怎么办、模型绕圈子时谁来叫停、谁对危险操作说不、出事之后怎么复盘、对话换人时历史给多少。这些都需要系统结构，而不是更长的提示词。

第 3 章 a 部分 · 逐块讲：每块解决什么，缺了会怎样

模型（Model）

理解自然语言、在开放情况下做决策。每个 agent 可以用不同模型（分诊用快而便宜的，专家用强的），运行配置可全局覆盖；支持 OpenAI 之外的 100 多种模型。

缺了它：只能写死规则，用户换个说法就失效。

指令（Instructions）

定义角色、做事步骤和边界。可以是固定文本，也可以是根据上下文动态生成的函数。交接场景推荐加官方前缀 RECOMMENDED_PROMPT_PREFIX，让模型明白“你可能是被转接过来的”。

缺了它：模型按通用助手行事：答非所问、越权承诺、风格不一。

工具（Tools）

取得真实数据、执行真实动作。工具同时也是权限边界：模型只能做你暴露给它的事，参数校验和鉴权在代码里完成。

缺了它：模型只能凭记忆编答案（幻觉），说“已为您退款”但实际什么都没发生。

交接（Handoffs）

把对话交给更合适的专家，并切换指令和工具集。让每个专家的提示词短而专注，可单独测试。

缺了它：一个巨型提示词装下所有业务，规则互相干扰，改一处坏三处。

约束（Guardrails）

在模型之外独立检查输入、输出和工具调用。可以用便宜模型或纯规则，提前拒绝明显不该做的请求。

缺了它：安全全靠模型自觉；提示词注入、跑题滥用、违规承诺直接到达用户或业务系统。

观测（Tracing）

记录每一步：谁、在第几轮、看到了什么、做了什么、花了多久。是排查、评估、回归测试和合规审计的共同基础。

缺了它：出了问题只能猜；无法向审计说明“为什么退了这笔钱”。

此外还有两个“粘合件”：Runner 负责把六块按规则串起来；人工审批（human-in-the-loop，人工介入）负责在高风险动作前把控制权交还给人。后者是在社区强烈要求下才加入的（见本章 c 部分规则六）。

第 3 章 b 部分 · 各部分之间具体怎么交互

以“用户申请退款”为例，一次 Runner.run 中各块按下面的顺序参与（与下方模拟器一一对应）：

  1. 观测RunnerRunner 打开一条 trace（建议设置 workflow_name，并用 group_id 把同一会话的多条 trace 串起来），为当前 agent 打开 agent span。从会话中取出历史，与新输入合并（合并方式可用 session_input_callback 定制）；调用模型前，call_model_input_filter 还有最后一次机会修剪或脱敏输入。
  2. 约束只在第 1 轮：Runner 把第一个 agent 的输入约束分成两组——阻塞组先跑完，并行组与模型调用同时启动。 run.py#L1776
  3. 模型指令Runner 把“当前 agent 的指令 + 对话历史 + 工具清单（函数工具、交接工具、MCP 工具）+ 输出格式要求”发给模型，记为 generation span。注意：交接对象在模型眼里也只是工具清单中的一项。
  4. Runner把模型返回解析成几类东西：普通消息、函数工具调用、交接调用、MCP 审批请求、Shell/改文件/电脑操作等。
  5. 工具同一轮的多个函数工具默认全部同时启动。每个工具依次经过：审批判定 → 工具输入约束 → 执行（function span）→ 工具输出约束。结果被追加为一条“函数调用输出”——工具结果不直接给用户，而是成为下一轮模型输入的一部分，由模型决定怎么用。出错时默认也转成一句模型能看懂的错误文本。
  6. 交接若有交接调用：执行 on_handoff 回调（例如记录转接原因）→ 用 input_filter 决定新 agent 看到哪些历史 → 当前 agent 切换，新 agent 的指令和工具集整体替换旧的 → 记为 handoff span。历史默认完整传递；你的运行上下文对象在整次运行中共享。注意：输入约束不会因为换了 agent 而重跑。
  7. Runner按优先级规则判定下一步：暂停等审批、换人再来、结束、还是再来一轮（见 c 部分）。每进入新一轮计数加一，超过 max_turns 立即停止。
  8. 约束观测得到最终输出候选后，运行最后那个 agent 的输出约束；通过则返回结果、写入会话、关闭 trace（后台批量导出）。触发则抛出异常，被拒的候选回复不写入会话。

追踪把这些步骤串成一棵树：trace → task span（一次运行）→ turn span（一轮）→ agent span → generation / function / handoff / guardrail span。span 通过 Python 的上下文变量自动挂到“最近的当前 span”下面，所以开发者不用手动传父子关系。 tracing/create.py

第 3 章 c 部分 · 规则是怎么设计的、怎么串起来的

规则一：“这一轮结束了没有”——一个有优先级的判定

文档用一句话概括：“模型产出了期望类型的文本输出、并且没有工具调用”，才算最终输出。源码里每轮结束时的判定按固定顺序进行： turn_resolution.py#L1126 run_steps.py

  1. ①
    有待审批的工具调用 → 暂停（NextStepInterruption）。不需要审批的同轮工具照常执行，结果保存，等人决定后再继续。
    产品逻辑：没有人点头之前，任何依赖它的后续都不能发生，所以审批排第一。
  2. ②
    有交接 → 换人，再来一轮（NextStepHandoff）。同一轮如果模型要求了多个交接，只执行第一个，其余回复“检测到多个交接，忽略此项”。 #L578
    产品逻辑：交接意味着“换个负责人”，当前 agent 这一轮的结论不再作数推测；同时只能有一个负责人，避免对话分叉。
  3. ③
    工具结果按 tool_use_behavior 被认定为答案 → 结束。
    产品逻辑：有些工具的输出本身就是交付物，不必再让模型复述一遍。
  4. ④
    没有待执行的工具、且有消息 → 校验后结束。设了 output_type 就必须通过校验；模型拒答则走 ModelRefusalError 或兜底；纯文本直接作为最终输出。
  5. ⑤
    其余情况（执行了工具）→ 再来一轮（NextStepRunAgain），轮次加一；超过 max_turns 就停止。

这套优先级的好处是行为可预测：同样的模型输出，永远走同样的分支。对产品方的启示是：如果你希望某件事“一定发生在回复之前”（比如记录工单），要么做成工具让模型调用，要么放在 Runner 之外的代码里，而不是寄希望于模型“记得”。

规则二：工具使用策略——强制、停止与防死循环

  • 是否强制用工具：tool_choice 可设为 auto（模型自己决定）、required（必须用某个工具）、none（不许用）或指定某个工具名。
  • 防死循环：reset_tool_choice 默认为真——用过一次工具后自动恢复成 auto。否则会出现“被强制用工具 → 结果回到模型 → 又被强制用工具……”的无限循环。 agent.py#L396
  • 用完工具后是否停止：tool_use_behavior 有四种——run_llm_again（默认，结果交回模型再组织回复）、stop_on_first_tool（第一个工具的结果就是最终答案）、StopAtTools([...])（调用了指定工具才停）、自定义函数（由你的代码判断）。 docs/agents.md
  • 两个并发旋钮：parallel_tool_calls 控制模型能否一次发出多个调用；max_function_tool_concurrency 控制 SDK 实际同时执行几个（默认不限）。
  • 调用了不存在的工具：默认直接报错（ModelBehaviorError）；可改为把错误告诉模型、让它重选（return_error_to_model）。 run_config.py#L498

背后的考虑：“工具结果就是答案”能省一次模型调用、避免模型改错数字（例如报价），但也意味着输出约束看到的是工具的原始结果；文档专门写了这种情况下被拒的工具输出会被替换成“该输出已被输出约束拦截”的占位文本，原始内容不进入会话。默认值选择“再交回模型”，是因为大多数工具结果需要被翻译成人话。

规则三：交接的过滤规则——新 agent 能看到多少

  • 默认全量：交接时“就像新 agent 接管了对话，能看到之前的全部历史”。
  • 优先级：单个交接上的 input_filter 优先于全局的 RunConfig.handoff_input_filter。 handoffs#L158 run_config.py#L377
  • 现成过滤器：remove_all_tools 去掉历史里所有工具调用条目——但文档提醒，它不会清除已经写进普通消息里的工具内容。 handoff_filters.py#L33
  • 压缩历史（测试版，默认关）：nest_handoff_history 把可摘要的历史压成摘要段。文档强调：“它改变历史的表现形式，但不做脱敏”。
  • 动态开关与附带信息：is_enabled 可按运行时条件开关某个交接（在模型回复前评估，因此不能用来校验交接参数，校验要放在 on_handoff 开头）；input_type 让模型交接时附带“原因、优先级”等小块元数据。
  • 不支持的组合：使用服务器端会话（conversation_id 等）时，交接过滤器无效；如果接收方绝对不能继承历史，应另起一次运行。

背后的考虑：默认全量是为了“转接后不用让用户再说一遍”；但历史越长，新 agent 越容易被前一个 agent 的风格和工具噪音干扰，也越可能看到不该看的数据。SDK 的态度是给出开关、写明边界，由产品方决定“转接时交代多少背景”。

规则四：约束的并行/阻塞与触发时机

  • 谁的约束在什么时候跑：输入约束只对第一个 agent、只在第 1 轮；输出约束只对产出最终输出的 agent；工具约束在每次受保护的函数工具调用前后。交接和托管工具不走工具约束管道。
  • 并行（默认）：run_in_parallel=True，约束与模型同时开始，响应最快；但如果触发，主模型“可能已经消耗了 token、执行了工具”才被取消。 guardrail.py#L100
  • 阻塞：run_in_parallel=False，约束跑完才启动模型，触发时“agent 根本不会执行”，适合省钱和避免副作用。
  • 输出约束总是在 agent 完成后运行，不支持并行。
  • 触发后：立即抛出 InputGuardrailTripwireTriggered / OutputGuardrailTripwireTriggered，异常里带着是哪条约束、以及到目前为止所有约束的结果，方便应用层决定怎么回复用户。

背后的考虑：这是“体验 vs 安全成本”的典型取舍。默认并行是因为绝大多数请求是正常的，不该为少数恶意请求让所有人多等一次检查；而“一旦启动就有副作用”的场景（比如首轮就可能调用写操作工具），应切换为阻塞，或者用工具约束和审批守住真正危险的那一步建议。

规则五：上限与兜底

  • max_turns 默认 10（Python 与 JS 版一致），可设为不限。超过即抛出 MaxTurnsExceeded，并在追踪里给当前 span 标上“超过最大轮数”。 run.py#L1605 JS constants.ts
  • error_handlers 支持三种错误的兜底：max_turns、model_refusal、invalid_final_output。处理器返回一个受控的最终输出，而不是让整个请求报错；include_in_history 决定这条兜底要不要写进会话。 run_error_handlers.py
  • 单个工具可设超时，默认把“超时了”作为结果告诉模型，也可以改成直接失败；agent-as-tool 的子运行有自己的 max_turns。

背后的考虑：10 轮是一个“正常任务够用、失控时及时止损”的默认值。更重要的是兜底处理器的设计：它承认“没能完成”也是一种需要设计的产品结果，并刻意规定兜底不会重试模型、也不会重放工具副作用，避免“兜底时又退了一次款”。

规则六：人工审批与中断

  • 声明：工具上写 needs_approval=True，或给一个函数逐次判断（例如金额大于 500 才需要）。适用于函数工具、agent-as-tool、Shell、改文件，本地 MCP 服务器用 require_approval。 tool.py#L500
  • 范围是整次运行：交接后的 agent、嵌套在 agent-as-tool 里的工具，审批请求都会冒泡到最外层统一处理。
  • 暂停—保存—恢复：result.interruptions 列出待审批项 → result.to_state() 得到可序列化的运行状态（可以存进数据库，隔天再处理）→ state.approve(...) / state.reject(...) → 用最初的顶层 agent 和这个状态再次 Runner.run，从断点继续。可以只处理一部分审批，剩下的会再次暂停。 docs/human_in_the_loop.md
  • 失败时关闭：判断函数需要看参数；如果参数缺失、不是合法 JSON、不是对象等，判断函数不会被调用，直接要求人工审批。
  • 粘性决定：always_approve / always_reject 对同一工具后续调用生效；但 Shell 和改文件工具的粘性决定不区分 agent，文档专门警告了跨 agent 被误放行的风险。
  • 中断：流式运行可 cancel() 立即停止，或 cancel(mode="after_turn") 等当前轮结束再停。 result.py#L941

取舍与替代方案

集中、固定优先级的规则让行为可预测，灵活性则通过钩子补回来：call_model_input_filter（改模型输入）、生命周期钩子（hooks）、自定义 tool_use_behavior、错误处理器。替代方案有两种：一是完全手写循环（最灵活，但每个团队都要重新踩一遍边界情况的坑）；二是图式工作流引擎（每一步显式定义，最可控，但开放式任务里要预先画出所有分支，写起来很重）。Agents SDK 站在中间：默认让模型驱动，关键节点由规则和代码兜住。

要点小结
  • 判定顺序：审批 > 交接 > 工具结果即答案 > 校验后的最终输出 > 再来一轮；每轮计数，超过 max_turns 即停止。
  • 工具结果回到模型而不是用户；交接替换指令和工具集，历史默认全量传递；约束只在特定 agent、特定时机生效。
  • 并行约束换来低延迟，代价是触发前可能已产生开销；高风险动作用阻塞约束、工具约束或审批守住。
  • “没完成”也要设计：用错误处理器给出受控兜底，且兜底不重放副作用。

产品洞察一：约束放两头，审批放在动作上

产品洞察二：输出约束要挂在“每个可能说最后一句话的 agent”上

因为 SDK 的输出约束只对产出最终输出的 agent 生效，交接架构下，只给分诊 agent 配输出约束等于没配——最后说话的是专家。更稳妥的做法是给所有专家挂同一组输出约束，或者通过运行配置（RunConfig.output_guardrails）全局添加。 docs/running_agents.md

产品洞察三：记忆和观测是“层”，不是“步骤”

它们不在某个箭头上，而是每一步都要读写：会话层决定下一回合模型能看到什么；观测层记录每一步发生了什么。把它们画成两侧贯穿的层，是在提醒：换模型、加 agent、改流程时，这两层都不应该需要重做。

第 5 章

agent 应该怎么设计，而不是遇到什么都做成 agent

一句话结论agent 是“把控制流交给模型”的那一档方案：它换来面对开放情况的灵活，付出的是确定性、延迟、成本和可评估性。设计时先问“能不能不用它”，从最低一档起步，用数据证明需要再升级。

问题背景：什么都做成 agent 的代价

“agent 化”很诱人：写几句指令、挂几个工具，似乎什么都能做。但每把一个决定交给模型，就多一个不确定点：同样的输入可能走不同路径；每多一轮就多一次延迟和费用；结果难以写成断言测试；出了事也难以解释。Agents SDK 的文档本身就把“用代码编排”和“让模型编排”并列，并明确说前者“在速度、成本和效果上更确定、更可预测”。 docs/multi_agent.md 仓库的模式示例里，第一个就是“确定性流程”：把任务拆成固定步骤，每一步一个 agent，上一步的输出作为下一步的输入。 agent_patterns/README.md

产品洞察一：六个判断维度

① 任务确定性

同样的输入是否应该总有同样的输出？越确定越不需要 agent。“把订单状态翻译成文案”很确定；“帮我规划一次旅行”不确定。

② 步骤能否枚举

能事先画出流程图吗？能画出来就用代码或固定工作流写死；画不出来（步骤取决于中途发现的信息）才需要模型决定下一步。

③ 出错代价

错一次是“换个说法重来”还是“钱打错了账户”？代价越高，越要压低自主度，或给 agent 加审批与输出约束。

④ 是否需要多轮探索

需要“查一下、看结果、再决定查什么”吗？这正是 agent 循环的价值所在；一步就能得到答案的任务，用单次调用即可。

⑤ 延迟与成本预算

用户愿意等 2 秒还是 2 分钟？agent 每多一轮都是一次完整模型调用。实时交互、高并发场景，预算往往不允许多轮。

⑥ 可评估性

能写出“什么算对”的检查吗？难以评估的任务做成 agent，等于上线后不知道它是变好还是变坏。文档也把“投资评估”列为让模型编排的关键前提。

产品洞察二：五档方案阶梯

决策器：这件事该不该做成 agent？

产品洞察三：升级要有证据，降级要有勇气

升级路径：先用最低可行档位上线，用追踪数据观察哪些请求处理失败、失败在哪一步，再决定是否升级。例如分类准确率不够，先改进单次调用的提示词和输出结构，而不是马上改成 agent建议。

降级路径：agent 上线后，追踪里常会看到某些路径反复以同样方式出现（例如“查订单 → 判断是否重复扣款 → 退款”）。这类稳定路径应该被固化成工作流，只把真正开放的部分留给 agent。这样更快、更便宜、更好测建议。

中间形态：SDK 里有很多“半自主”的旋钮可以组合使用：tool_choice="required" 强制先查数据再回答；StopAtTools 让某个工具一被调用就结束；max_turns 设小一点限制探索深度；is_enabled 按用户等级开关某些交接。不必在“全自动”和“全写死”之间二选一。

具体例子

  • 发票字段抽取：需要理解版式各异的文字，但一步完成、易于评估 → 单次 LLM 调用 + 结构化输出。做成 agent 只会更慢更贵。
  • 电商退款客服：步骤取决于查到的订单情况，需要边查边决定，退款有资金风险 → 单 agent + 工具，退款工具按金额要求审批，回复加输出约束。
  • 多业务线客服中心：机票、酒店、会员积分规则完全不同 → 分诊 + 交接的多 agent，每个专家单独评估。
  • 修复代码 bug：需要多轮探索（读代码、跑测试、再改），可通过测试自动评估 → 单 agent + 沙箱工具，参考 Codex 的沙箱与审批档位。

取舍与替代方案

这个框架的风险是“过于保守”：有些任务看似步骤可枚举，实际长尾情况很多，写死的工作流会在长尾上频繁失败。折中方案是“工作流为主干，agent 处理异常分支”：主流程用代码写死，遇到工作流处理不了的情况，再交给一个 agent 兜底建议。

要点小结
  • 六个维度：确定性、可枚举性、出错代价、探索需求、延迟成本预算、可评估性。
  • 五档阶梯：普通代码 → 单次调用 → 固定工作流 → 单 agent + 工具 → 多 agent，从低档起步。
  • 把 agent 里反复出现的稳定路径固化成工作流；高风险动作无论哪一档都要有审批。
第 6 章

边界场景的处理逻辑

一句话结论SDK 对大多数边界情况的默认策略是“把错误变成模型能看懂的信息，让它自己恢复”；只有在恢复会带来更大风险时（越界、超限、约束触发）才中止。产品方要做的，是为每一种“中止”设计用户看得到的结局。

问题背景

agent 产品的用户体验，很大程度上由失败时的表现决定。用户能接受“我暂时查不到库存，已为你转人工”，不能接受一个转圈半分钟后弹出的英文报错。下面十种场景，每条都说明 SDK 默认怎么做、用户应该看到什么、以及背后的产品考虑。点击展开。

① 工具报错 默认：把错误变成一句话交给模型
SDK 默认
函数工具抛异常时，默认的错误处理函数返回固定文本“运行工具时发生错误，请重试”给模型——刻意不把异常细节暴露给模型（源码注释：如需返回细节，请提供应用认可的错误函数）。设为 None 则直接抛出，由你处理。超时默认也作为结果告诉模型（timeout_behavior="error_as_result"）。
用户体验
模型通常会重试或换个说法告诉用户；用户不应看到堆栈或内部系统名。
产品策略
读操作可以放心让模型重试；写操作（扣款、发信）必须幂等，否则“重试”可能变成“重复执行”建议。不暴露异常细节，是防止内部信息经由模型泄露给用户。

⑥ 并行工具调用 默认：同一轮的函数工具全部同时启动
SDK 默认
模型一次发出多个函数调用时，SDK 默认全部同时执行；max_function_tool_concurrency 可设上限；parallel_tool_calls 控制模型能否一次发多个。审批可以只处理一部分，已批准的继续，未处理的再次暂停。同一轮多个交接只执行第一个。
用户体验
并行查询让等待更短（同时查库存和物流）。
产品策略
读操作适合并行；有先后依赖或会互相影响的写操作（先取消旧订单再下新单）不应依赖模型自觉排序，可以合并成一个工具，或关闭并行建议。对外部接口有限流时设置并发上限。

⑦ 流式中断与取消 默认：cancel() 立即停止
SDK 默认
result.cancel() 立即停止；cancel(mode="after_turn") 让当前轮干净结束再停。文档提醒：流式运行在 stream_events() 结束前并没有真正完成，SDK 可能仍在写会话、整理审批状态。如果在输出约束运行时立即取消，正在运行的约束会被取消，也不会写入最后一轮的会话。用户在暂停期间补充的新输入可用 state.add_input 暂存，下次调用模型前加入。
用户体验
“停止生成”按钮应立即生效；若当前轮正在执行写操作，提示“正在完成当前步骤后停止”更诚实。
产品策略
立即取消适合纯生成，“本轮后停止”适合有工具副作用的运行，避免停在“钱扣了、记录没写”的中间态建议。参见 issue #329。

⑧ MCP 服务断连 默认：剔除失败的服务器，用剩下的继续
SDK 默认
MCPServerManager 默认 drop_failed_servers=True：只把连上的服务器暴露给 agent，失败记录在 failed_servers 和 errors；reconnect(failed_only=True) 只重连失败的；strict=True 则首个失败就报错。连接和清理超时默认 10 秒。MCP 工具调用失败默认转成模型可见的错误文本。实时会话里，服务器正常关闭连接会产生“已断开”事件并正常结束，非预期故障才走异常。
用户体验
部分能力降级（“暂时查不了库存”），而不是整个助手不可用。
产品策略
对核心依赖用 strict 或启动检查，对锦上添花的服务允许降级；在指令里告诉模型“某些工具可能不可用时如何回复”建议。

⑨ 敏感数据不进追踪 注意：默认会记录模型与工具的输入输出
SDK 默认
trace_include_sensitive_data 默认为真：generation span 和 function span 会记录模型与工具的输入输出。可在运行配置里关闭，或用环境变量设置默认值；关闭后模型 span 不记录请求和响应内容，被拒绝的审批只记通用文本。语音 span 默认包含音频数据，有单独开关。使用零数据保留（ZDR）政策的组织无法使用追踪。需要脱敏导出时，应把“脱敏 + 发送”放在同一个自定义导出器里，脱敏失败就丢弃整批。
用户体验
用户看不到，但这是信任问题：客服对话里的手机号、地址不应出现在调试平台上。
产品策略
开发环境开、生产环境默认关，或只对抽样请求开；运行上下文（不发给模型的对象）是放用户身份信息的更好位置建议。默认开启的取舍是“调试优先”，产品上线前必须主动复查。

⑩ 需要人工审批 默认：暂停运行，状态可保存后恢复
SDK 默认
需要审批时运行暂停，interruptions 列出待审批项（含 agent 名、工具名、参数）；状态可序列化后存储，人工处理后从断点恢复。参数无法解析时“失败即关闭”，直接要求人工审批。被拒绝时返回给模型的文本可全局或逐次定制（如“主管拒绝了该退款，请向用户说明并提供替代方案”）。
用户体验
用户看到“已提交主管审核，预计 10 分钟内处理”，而不是一直转圈；审批人看到的应是清晰的参数（金额、订单号），而不是原始 JSON。
产品策略
按金额/动作类型分级审批，避免审批疲劳；慎用“总是批准”，尤其是 Shell/改文件这类不区分 agent 的粘性决定。参考 Codex：把“能做什么”和“何时问人”拆成两个旋钮。

产品洞察：默认“可恢复”，例外“必中止”

把十条放在一起看，SDK 的默认取向很清楚：工具报错、超时、找不到工具（可选）、MCP 部分失败，都转成模型能理解的信息，让循环继续——因为 agent 的价值就在于能自我修正。而越过安全边界（约束触发）、越过资源边界（超过轮数）、需要人的判断（审批），则一定中止或暂停，把决定权交回应用。产品方的职责是给每个“中止”配一个用户看得懂的结局，并用追踪统计各类中止的频率。

取舍与替代方案

“交给模型自行恢复”的代价是：错误可能被模型“圆过去”，用户拿到一个看似正常但缺了数据的回答。如果你的业务不能接受这种情况（例如财务报表），应把关键工具的错误处理设为直接抛出，让失败显性化建议。

要点小结
  • 可恢复的错误默认交给模型；越界、超限、需要人判断时中止或暂停。
  • 追踪默认记录敏感数据，上线前必须复查；交接的压缩历史不等于脱敏。
  • 写操作要幂等；取消和审批都要考虑“停在中间态”的问题。
